# Organization server

FastAPI service, strict Pydantic authentication DTOs, shared JSON Schema numerical observations, SQLAlchemy transactions, PostgreSQL deployment migrations, Brevo adapter and durable numerical rollups. Personal mode does not require or contact this service.

## Local checks

From `apps/server`, run `uv sync --locked`, then `uv run python -m pytest -q` and `uv run ruff check aift tests`. Tests use explicit development SQLite databases with foreign keys enabled; they are not PostgreSQL race or production throughput evidence. PostgreSQL-specific integration tests use an explicitly supplied isolated `AIFT_POSTGRES_TEST_URL` and otherwise report skipped. Python imports require `packages/contracts/python` and `packages/estimator/python` on `PYTHONPATH`. Both packages' adjacent `schema` and `data` directories must ship with the Python modules. The Dockerfile preserves this layout.

## Configuration and production start

Set `AIFT_SETTINGS_FILE` to a protected JSON file outside the repository. `aift.config.Settings` is the complete validated configuration schema. Required values include a PostgreSQL SQLAlchemy URL, exact HTTPS registration/operator origins, hosted domain or a single self-host origin, approved extension origins, independent authentication encryption and lookup keys, Ed25519 deletion signing seed, protected deletion-journal path, approved Brevo key/sender and verified routing/privacy setup.

Use a Fernet key for `encryption_key` and an independent cryptographic 256-bit random `lookup_key` secret. Two operator settings, `person_analytics_enabled` and `ip_collection_enabled`, both `false` by default, decide whether administrators get per-person views and whether connection addresses are collected; see `docs/operations/SELF-HOSTING.md` and `docs/implementation/CONTRACTS.md` section 8, including what must be done before switching either on. With IP collection off, `ip_key`, `ip_keys`, `active_ip_key_version`, `ip_restore_required_until` and `ip_retention_days` are not required, a settings file that still contains them keeps starting because the keys are accepted and ignored, and `/v1/config` sends `ip_retention_days: 0` so that older extensions keep working; with it on they are required and validated as before. `deletion_signing_key` is a base64url-encoded 32-byte Ed25519 seed. Keys must be protected and backed up separately from the database. Never print secrets in terminal transcripts, checked-in examples or application logs. Production requires `environment: "production"`, `mail_adapter: "brevo"`, `policy_confirmed: true`, `routing_verified: true`, `mail_privacy_verified: true`, and `restore_journal_verified: true`. These switches record externally completed checks, not substitutes for those checks. Missing essentials stop startup with `configuration_required`.

Owner-approved hosted policy is 50 active memberships including administrators and one active organization per work domain with operator-reviewed exceptions. Use `member_capacity: 50`, `domain_policy: "one_active"`. Support, privacy and security contact: `pranitnale42@gmail.com`. Source: [AI Footprint Tracker](https://github.com/pranitnale/AI_Footprint_Tracker). Copyright holder: Pranit Jagannath Nale. Self-host operational limits remain configurable and usage retention defaults to until admin deletion.

Run `uv run alembic upgrade head` from this directory with `AIFT_SETTINGS_FILE` set to protected configuration. Current migration head is 0012. Migration 0011, a preproduction upgrade, clears obsolete usage, imported history, receipts and derived calculations; authentication, preferences, ownership and erasure markers remain intact. It adds historical dependency hashes and snapshots to current engine estimates. Migration 0012 adds the company deduplication columns (the server's hash of a record's company key and whether another member's record counts it) to live and saved records; existing records carry no key and count as before. Readiness and the restore gate require schema version 12. Only observation, usage-batch and history schema `2.0.0` is accepted. Original formula calculations retain their existing arithmetic inside the current `2.0.0` result envelope. ## Mail privacy release gate

The official [Brevo 21 July 2026 clarification](https://developers.brevo.com/changelog/2026/7/21) states that `contactPixelTrackingConsent: false` anonymizes open events and is ignored when the feature is disabled. It does not establish removal of tracking pixels. Therefore production OTP is blocked until a separately verified Brevo configuration passes the project's no-pixel/no-rewritten-link delivered-MIME tests. This implementation sends only a minimal plain-text code message and `contactPixelTrackingConsent: false`; it does not claim that those fields alone satisfy the gate. No real mail was sent during implementation. `FakeMail` is available only in explicit test/development, never production.

Dispatch records and encrypted transient payloads commit before contacting Brevo. The worker claims each dispatch before sending; interrupted or timed-out delivery is unknown, never automatically retried with a fresh redeemable code. Explicit resend observes cooldown and invalidates the preceding code. OTP API acceptance is labeled accepted, not delivered.

## Transactions and aggregation

Tenant-scoped PostgreSQL transaction locks serialize same-tenant authorization/revision/deletion changes. Global registration domain claims and mail quotas use independent scoped locks. HTTP read snapshots use repeatable-read transactions without the tenant writer lock. Memberships, identities, installations, credentials, observations and rollups have relational keys, checks and tenant/owner foreign keys. Canonical occurrence/model/site columns and rollup period columns are indexed. Authentication secret-bearing protocol metadata remains encrypted in JSON columns where appropriate.

Original request/attempt revisions and durable ACKs commit atomically with affected daily/user/site/model rollups. Ordinary inserts and corrections apply fixed-size old/new contribution deltas; they do not rescan earlier day records. Corrections can decrease totals. Canonical day rebuild is reserved for identity reconciliation, deletion, timezone changes and detected inconsistencies. User/company queries stream rollup rows into bounded quantity/method/scope accumulators; distinct populations use SQL distinct queries across the whole range. Lists paginate in SQL. With sharing on, member company summaries show organization totals whatever the group size (owner decision of 13 October 2026): there is no minimum group size and no complementary suppression. A free model filter on the member company summary is still rejected. Administrators get organization aggregates only (owner decision of 17 and 18 October 2026): the server rejects a `user_id` filter on admin summaries, breakdowns, exports and recalculations and has no per-person request list. Aggregates are shown for any number of people, so in a very small organization they can reveal one person's usage.

Estimates call the shared Python reference; no server controller owns scientific coefficients. Resource groups keep method/hash/scenario/proxy/boundary separate. Missing work remains unknown. Pending unsupported methods remain visible until an approved compatible bundle is installed. Maintenance examines bounded pages; calculation failures are safely recorded and retried without rewriting original results. Exact PostgreSQL performance at the 500-member and 1M/10M-record workload remains an unverified release gate.

## Maintenance, retention and restore

Run `uv run python -m aift.maintenance serve` continuously; use `run` for a single bounded maintenance tick. It expires request families at the company-local calendar-day cutoff of the organization's usage retention (the plan's limit or the administrators' shorter choice; hosted free and self-hosted usage is kept until an administrator deletes it unless a shorter period is chosen), deletes abuse-protection rows one day after their last request, purges expired authentication secrets/exports, applies acknowledged scheduled plan changes and reconciles canonical data against rollups. Use the same protected settings file and Python paths as the API. Do not run multiple overlapping maintenance jobs for one tenant outside the database locks.

Before a backup restore is available to users, restore protected keys and the independently retained deletion/expiry journal plus its authenticated `.head` checkpoint. With API traffic stopped, run migrations for the restored binary's compatible schema, then `uv run python -m aift.maintenance replay-journal`. Missing, truncated or undecryptable journal entries fail rather than being treated as empty; the chained head detects removal of trailing entries. Verify restored deletion epochs, expired-family exclusion, revoked users, export invalidation and aggregate state before enabling ingress. Keep `restore_journal_verified` false until the process is completed. The journal is encrypted and fsynced before erasure, must survive the normal database rollback window, and must be included in independent operational backup monitoring.

Keep database backups encrypted with a separately enforced disclosed expiry (proposed 30 days). Backup expiry, primary usage retention and Brevo mail-log retention are separate. Connected-device receipt coverage is reported independently from active-database erasure; offline profiles and already downloaded exports cannot be remotely guaranteed wiped.

## Stored connection addresses

With `ip_collection_enabled` off no new rows are written, and connection addresses recorded while it was on stay in the `network_observations` table until they are deleted, shown to no one. Deleting a person still deletes that person's rows. `uv run python -m aift.maintenance purge-network-observations` only counts the stored rows. After the owner confirms it, the operator deletes every stored row with the one-off command `uv run python -m aift.maintenance purge-network-observations --confirm`, which deletes them in pages and reports how many it deleted; the empty table stays. It cannot be undone. Rate limiting still counts requests under a keyed hash (HMAC with `lookup_key`) of the connection's address. Key rotation applies only while IP collection is on; see [IP-KEY-ROTATION.md](IP-KEY-ROTATION.md).

## Migration, maintenance and restore release gates

Run `uv run alembic upgrade head` from this directory with `AIFT_SETTINGS_FILE` set to protected configuration. Current migration head is 0009, including populated 0001 to 0002 auth/policy/session backfill, immutable approved method/history tables, scoped thread relations, separate numeric historical observations and engine overlays. Migrations 0004, 0005 and 0006 mark populated companies rebuilding so the bounded maintenance worker replaces legacy coverage groups, including separate extracted-file text projections, before totals or new ingestion are exposed; legacy exports are cancelled and their encrypted chunks are removed by maintenance. The 0002 migration invalidates legacy sessions and legacy export jobs whose recoverable CSRF/integrity format is incompatible. It does not erase canonical observations. [Parallel-engine compatibility](ECOLOGITS.md) documents the native EcoLogits dependency, selection API, recalculation and restore behavior.

Migration 0008 retains legacy deletion tombstones as `legacy_unknown`; they conservatively block historical reimport. New live age-cleanup tombstones are identified as `retention`. Imported numeric history is retained until explicit deletion, including source dates older than the organization's live usage retention window. Source dates retain their provider basis and microsecond precision, while import time establishes the authenticated enrollment scope. Historical counts, estimates and exports remain separate from live execution totals. Range deletion includes undated historical rows, writes stable erasure markers and participates in protected journal replay after restore. See [the numeric history contract](../../docs/implementation/CONTRACTS.md#14-numeric-history-observed-while-the-user-loads-a-conversation) for API limits and overlap exclusions.

The container uses repository root as build context and runs `uvicorn aift.main:production_app --factory --host 0.0.0.0 --port 8000 --no-access-log` in its pinned virtual environment. Start a separate process with `python -m aift.maintenance serve`; probe it with `python -m aift.maintenance health`. Each bounded tick persists a heartbeat and cursor. API readiness requires current schema and recent worker heartbeat. Top-level ingress owns static assets and SPA deep-link fallback; only server API/auth routes are proxied. No server is deployed by these commands in this repository.

Back up PostgreSQL plus protected auth/lookup/signing keys and the append-only deletion journal with its authenticated `.head` checkpoint. Also preserve installed approved method bundles/trust configuration, which are required to reproduce historical views. Restore into an offline isolated target, migrate to head, and replay deletion before opening ingress. `uv run python tools/verify_restore.py` prints the gate requirements without connecting. `--execute --confirm-offline-restore` replays the journal on the configured approved PostgreSQL restore target, rejects unfinished erasure and streams canonical/rollup reconciliation. Do not use a stale checkpoint or omit erasure replay.

`uv run python tools/benchmark_server.py --records 1000000` prints the unexecuted 500-user/two-installation load plan. Explicit execution requires an approved PostgreSQL runtime in `AIFT_BENCH_DATABASE_URL` and `--execute --confirm-isolated-schema-writes`; it creates and removes only a uniquely named test schema. Repeat with 10000000 retained records for the large-history gate. The harness seeds canonical histories, measures 50 observations/second and dashboard p95/storage, and reports thresholds honestly. PostgreSQL migration, transaction races, performance and real restore remain release gates: local Windows Application Control denied runtime start, and no bypass or production runtime was used. Portable migration, restart, backup/restore and adversarial tests are executed separately.

Restore verification now performs a bounded per-tenant maintenance drain after journal replay. `tools/verify_restore.py --execute --confirm-offline-restore --max-worker-ticks 10000` requires the existing explicitly approved PostgreSQL target; the configurable additional worker budget is 1..1000000 ticks. If rebuilding or erasure remains at the limit, it exits with `restore_work_incomplete` and leaves ingress closed. The persisted cursor permits a reviewed retry. The gate also derives required day/site/model/owner rollup identities from canonical records, rejects missing projections even when the rollup table is empty, and verifies both current canonical totals and stored payload bytes against each checksum. Its report includes `worker_ticks` and `canonical_records_covered`. Unexpected failures produce only `restore_verification_failed`, never raw database/configuration exception text. SQLite regression fixtures exercise this same helper through a real backup and Alembic upgrade; they do not replace the production PostgreSQL restore requirement.
