# Local text counting

`countText({text, modelId, profileId?, jobId, revision})` is the low-level single-text interface. It runs in a packaged worker and returns `{measurement, assetHash, profileId, encoding, modelExactness, status, jobId, revision}`. Text exists only in worker memory; no external counting endpoint, persistence or logging is used. The tokenizer merge cache is disabled to avoid retaining captured text between jobs. Input is capped at 8 MiB UTF-8.

The extension worker uses the stricter `CountRequest` and `CountResponse` envelope through `countFields`. A request identifies the job, revision, implementation, profile and an allowlisted set of `input`, `answer`, `thinking` and `file_0` through `file_15` fields. Responses retain those identities and contain only validated `TokenResult` values. A response can be `partial` when one bounded field is unavailable and another field was independently counted. Envelope, job, revision, implementation, profile or asset mismatches make the whole response unavailable. Cancellation uses a separate `{type: "cancel", jobId, revision}` command.

`TokenizerImplementation` is the small injection interface for a packaged implementation. Each implementation declares one ID and immutable profile descriptors, then counts one transient `TokenJob`. The boundary rejects an implementation/profile combination unless exactly one declared profile matches. A new profile also needs an approved `TokenMeasurement` profile ID in `@footprint/contracts`; injection does not bypass the stored schema allowlist.

Browser hosts, page scripts and UI import `@footprint/tokenizers/metadata`. It exports worker DTOs/validation, immutable profile descriptors from `manifest.ts` and runtime configuration without importing the encoder or vocabulary graph. Dedicated counting/file workers import `@footprint/tokenizers/worker`, which adds the packaged loader in `bundled.ts` and orchestration in `counting.ts`. The root entrypoint retains the complete API for existing developer callers; production metadata consumers must not use it.

`runtime.ts` defines the trusted composition metadata shared by callers, workers and response validators. `createCountingRuntime(manifest, profileId)` returns a frozen `CountingRuntime` with `selection: {implementationId, profileId}` and a metadata-only `manifest: {id, profiles}`. It copies profile descriptors, rejects duplicate/unapproved profiles and malformed asset hashes, and never retains the implementation's executable `count` function. `snapshotCountingRuntime` validates and copies an existing configuration before asynchronous work. `DEFAULT_COUNTING_RUNTIME` preserves the existing o200k selection and both bundled profile descriptors.

`validCountResponse` and `profileFor` accept `TokenizerManifest`; validation does not require loading or trusting an executable counter. A different implementation must still use an existing contract-approved profile ID, preserve the approximate evidence labels and numeric bounds, and return the exact selected profile/encoding/asset metadata. No worker response, message, private file or page can nominate a validation manifest or executable module.

The extension's `lib/counting-config.ts` exports only `PACKAGED_TOKENIZER_MANIFEST` and the selected `PACKAGED_COUNTING_RUNTIME`. Its executable counterpart, `lib/counting-worker-config.ts`, supplies `PACKAGED_TOKENIZER` only to counting/file workers. A packaged replacement must update the matching metadata and worker implementation; their equality is tested, and hosts reject wrong IDs/assets. Tests can inject real `CountWorkerRuntime`/`FileWorkerRuntime` instances and pass matching runtime metadata to `CountHost`, `FileCountHost` and `createCountingPlatform`. Passing metadata never loads code into another realm. Live/history job builders and inline/file receipt validators use the captured runtime rather than stamping bundled metadata on replacement results.

The source import gate rejects executable tokenizer imports from metadata/main-context modules. The extension build separately rejects encoder/counting modules rendered into main Vite chunks, including shared and dashboard chunks. Dedicated worker bundles are emitted as assets and remain allowed. This checks bundle placement, not native RAM or latency.

The default implementation is `gpt-tokenizer-4.0.0`. Its default is explicitly approximate `o200k-base-4.0.0-reference`; `cl100k-base-4.0.0-reference` is selectable. Known consumer model labels do not upgrade this mapping to exact. Counts can be exact for the supplied encoding and still be an unvalidated proxy for an undisclosed consumer model. `heuristic_estimate`, `observed_text` and `tokenizer_mapping_unverified` survive every result. Unknown explicit profiles fail closed. Literal special-token syntax is ordinary text.

Bundled BPE assets and their canonical-JSON SHA-256 hashes are in `src/assets.json`. Each encoding is loaded and verified once per worker lifetime. The dependency is `gpt-tokenizer` 4.0.0, MIT, by Bazyli Brzoska and contributors, https://github.com/niieani/gpt-tokenizer. Keep its license and OpenAI tiktoken asset notices in distribution. The 400 synthetic fixture corpus checks both encodings against official local tiktoken 0.14.0. This is not an accuracy claim about full provider requests or Google/Anthropic tokenizer compatibility.
