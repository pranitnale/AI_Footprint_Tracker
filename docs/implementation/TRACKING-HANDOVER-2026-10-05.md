# Tracking handover, 5 October 2026

This document is for anyone who changes the extension after the tracking work of 30 September to 5 October 2026, in particular during the planned refinements of the user interface. It records what the tracking does, how each AI tool's data was traced, which rules keep the figures correct, where the tests guard each rule, and how to check a tool live again.

**Read this before you change any file listed in section 9 ("Tracking-critical files").** The tracking was verified live on every supported tool and is covered by tests that fail when a rule is undone. In almost every case a UI refinement does not need to touch it. If you find something that looks wrong, prove it first (section 8 and section 10), then change it with a test that fails without your change. Do not "simplify" a rule because it looks unusual: most unusual rules exist because a provider's page behaves unusually, and the reason is written next to the code.

## 2. How tracking works, in one page

The extension never sends or scrolls on the user's behalf. It reads what the provider's own page sends and receives, and fetches only in two cases: the own read of an opened chat the page did not load in full (section 4.2), which is the setting "Load full chat history automatically", on by default and per site since 17 October 2026, and the download of each text file Perplexity Computer created (section 4.4).

```
provider page (MAIN world)
  capture.content.ts -> lib/capture-runtime.ts      wraps fetch, XHR and the ChatGPT socket
     live replies    -> packages/adapters/src/<site>.ts      protocol sessions -> snapshots
     saved history   -> lib/passive-history-text.ts, passive-thread-history.ts,
                        provider-history-stream.ts, claude-history-stream.ts, history-xhr.ts
                        -> packages/adapters/src/history/<site>.ts
        | window messages (structure, counts and text for local counting only)
content script (isolated world)
  entrypoints/content.content.ts   validates messages, binds them to the route, draws the bar
        | runtime messages
background service worker
  entrypoints/background.ts        tab addresses, routes, message routing
  lib/coordinator.ts               live captures, linking, publishing displays
  lib/history-service.ts           saved history: admission, counting, coverage
  lib/recorded-threads.ts          Perplexity thread links
  lib/company.ts                   organization mode uploads (no content)
  count.worker.ts                  token counting off the main thread
        |
packages/ledger      IndexedDB records: requests, attempts, history records, coverage
packages/estimator   EcoLogits (default) estimates, media methods, totals
        |
content script bar   lib/conversation-bar.ts, history-presentation.ts, estimate-details.ts
```

Key ideas:

1. **Two sources per conversation.** A *live capture* records a request and its reply while the user sends it. *Saved history* is what the page loads when a chat opens. A reply seen both ways must count once. The link between them is the provider's own ids: the request key (`provider_request_key`) and the reply key (`provider_attempt_key`). A saved reply linked to a live reply is "matched" in Details. A saved reply without a link is counted from history and, unless it can never have a live record, it shows as "unverified matching" and puts "≈" on Req.
2. **Records are never deleted by later reads.** History rows are upserted by message key (conversation, role, source id). A later read that no longer contains a message does not remove it. Totals count every request in a chat, including branches replaced by an edit (owner decision of 26 September, see section 5).
3. **Coverage.** Each conversation has a coverage row: whether the first request was proven (`first_request_verified`), the root message and the selected leaf. The newest observation wins, but a proven root stays proven while its row is current (`mergeHistoryCoverage` in `packages/contracts`). "Partially loaded" is shown only when the first request is not proven, in Details under "Not everything could be counted" on every site. Until 14 October 2026 ChatGPT offered "scroll to the first message" as its action; the tracker now reads a long ChatGPT chat's missing pages itself (section 4), so no site offers an action for it (section 9).
4. **Fail closed, visibly.** Content the reader does not know makes a reply "Partly measured" in Details (owner decision of 2 October), never a silent zero and never a status on the bar. A response shape that cannot be read at all is refused and reported, not guessed.
5. **Text stays on the computer.** Prompts, answers, thinking text, documents, filenames and chat titles are never sent to the organization server. Message text is counted in the worker and then dropped; only lengths, counts and model ids are stored.
6. **Estimates.** Token counts and media facts go to the estimator. EcoLogits is the default and only selectable engine; the original method is never used as a fallback (owner decision of 16 September).

## 4. Each tool: what the page sends, how it was traced, what counts

All formats below were seen live between 30 September and 5 October 2026 on the owner's test accounts, from structure, counts, lengths and model labels only. Providers change these formats every few weeks, so check live before relying on a detail (section 8). Test fixtures are synthetic copies of these shapes.

### 4.1 ChatGPT (chatgpt.com)

**Live reply.** `POST /backend-api/f/conversation` returns an event stream. Known events are listed in `CHATGPT_EVENTS` in `packages/adapters/src/chatgpt.ts`: `delta` (JSON-patch style updates of the message tree, `delta_encoding` v1), `resume_conversation_token`, `input_message`, `title_generation`, `message_marker`, `server_ste_metadata` (served `model_slug`, `cluster_region`, timing), `message_stream_complete`, `conversation_detail_metadata`, `stream_handoff`, and unnamed `message` events. Some turns continue over the page's socket (`stream-item`, ending with `done` or `conversation-turn-complete`). An unknown event makes the reply partly measured.

*Message slots (seen 6 October, GPT-6 Astra).* One stream now carries several messages side by side: `c` 0 and 1 are assistant `thoughts` messages and `c` 2 is the answer. Each delta names its message with `c`, and a delta that omits `c`, `p` or `o` carries the previous value over (for example the closing `/message/status` and `/message/end_turn` patch of the answer has no `c`). The reader keeps one message tree per slot (`roots` in `chatgpt.ts`); before commit 2fa3328 it kept one tree, a thoughts patch hit the answer, and every live reply ended with `unsupported_schema`, shown as Tracking problem until a reload. Test: `chatgpt-turn.test.ts` ("several messages in one stream"). Checked live after the fix: test C5 ended completed with no failure, served `gpt-6-astra-wm`, and the bar showed the same totals live and after a reload (Req 4, 42/8 tokens, 0.929 Wh).

*Socket hand-over with an aborted body (seen 18 and 19 October, every new reply, GPT-6 Pro).* The request body now carries only `delta_encoding`, `resume_conversation_token`, `stream_handoff` (options `resume_sse_endpoint` and `subscribe_ws_topic` with one topic) and `[DONE]`; the page then aborts the body (`AbortError: BodyStreamBuffer was aborted`), subscribes to the topic on its socket (`offset` 0) and reads the reply there. Each socket frame is an array of envelopes `{type: "message", topic_id, payload: {type: "conversation-turn-stream", payload: {type, conversation_id, turn_id, ...}, metadata}, offset}`; a `stream-item` holds `encoded_item`, the same server-sent event text the body used to carry (delta slots included, several items can restart with `delta_encoding`), with `stream_item_id` and `parent_stream_item_id`; a `heartbeat` item carries no output; `done` ends the turn; `conversation-created` and `conversation-turn-complete` follow on the `conversations` topic. Before the fix the capture runtime turned the abort into a failed read (`capture_interrupted`), dropped the capture and ignored the socket items, so every reply showed Tracking problem and "Reply not counted", and Req showed "≈" once history counted the reply. Now a body read error after the stream named a topic ends the body like a normal end (`handedOff` in `observe`, `lib/capture-runtime.ts`); a cut frame still fails, an abort before the hand-over is still a failed read, and image jobs (no topic) keep their own rule. The capture then continues from the socket items as it did for the September hand-over, under the idle and total limits, and `heartbeat` is a known item (`CHATGPT_TURN_IDLE_ITEMS`). The socket wrapper only adds a message listener; frames reach the page unchanged and nothing is sent. Tests: `chatgpt-socket-handoff.test.ts` (the same record over the old body, the September hand-over and the aborted hand-over; abort before hand-over; image job). Not yet checked live after the fix (section 12). *Long socket replies (20 October 2026).* Each `stream-item` carries one delta in its own envelope, so a long reply sends thousands of items: a GPT-6 Pro reply of about 6,200 output tokens ended its live capture after about 4 minutes with `buffer_overflow` (stored as interrupted with that coverage reason; the figures then came from the saved chat), and a probe of another long Pro reply saw 174 socket frames and 1.05 MB in its first 10 minutes, the largest frame 116 KB, none near the 1 MB message bound. Either the 4,096 stream items the reader kept or the 8 MB of socket messages it counted ended the first reply; which one was not measured, as the test profile was signed out before a second reply finished. The stream items now have their own bound (`CHATGPT_STREAM_ITEMS`, 32,768, keeping only each item's id and a fingerprint of its content to recognise a resent item), and the reply's stream limit counts what the reader keeps (`retainedBytes`: its messages, delta trees and item ids) instead of the socket messages' size. Tests: `adapters.test.ts` ("more stream items than LIMITS.items") and `chatgpt-socket-handoff.test.ts` (5,000 items; socket data past the stream limit).

*Stop (19 October 2026).* The person's Stop sends `POST /backend-api/stop_conversation` with the chat's `conversation_id`; once it is answered 200, `lib/capture-runtime.ts` ends that chat's reply as stopped (`session.stopped()`), also while it runs on the socket. Since 19 October 2026 a turn ChatGPT took (its stream echoed the prompt with `input_message` or handed the turn over with `stream_handoff`) counts as started when it is stopped (`accepted` in `ChatgptSession.stopped`), so a stop before any message, as when GPT-6 Pro thinks without showing its thoughts, is `cancelled` with output 0 and Details lists "Stopped reply not estimated"; before, the unstarted reply kept its dispatch state in the coordinator and ended as `interrupted_unconfirmed` with unknown output. A reply cut off without a stop (a reload, a lost capture) keeps its unknown output. Tests: `chatgpt-socket-stop.test.ts`, `chatgpt-turn.test.ts` ("stopped after ChatGPT took it"). The stop request now also carries `exclude_async_types` (an object) beside `conversation_id` (seen 19 October 2026, evening).

*Stop in a new chat before ChatGPT names it (19 October 2026, evening).* In a new chat the page stays at `/c/local-chatgpt%3A<id>` until the reply ends, while the hand-over already named the real chat (a uuid unlike the local id, about 0.4 to 1 s after the send). Five live stops there between 1.8 and 3.9 s after the send (test Chrome, GPT-6 Pro) sent no `stop_conversation` at all: the page aborted the body before `[DONE]` and sent `[{"id": n, "command": {"type": "unsubscribe", "topic_id": <turn topic>}}]` on its socket, which answered `[{"id": n, "type": "reply", "reply": {"type": "unsubscribe", "topic_id": <turn topic>}}]`, and the page kept the local address. A stop before the send was answered (1.8 s in one run) also sent nothing; there the capture has no topic yet. In a saved chat the Stop sends `stop_conversation` first (answered 200) and then the same unsubscribe. Leaving the running new chat for a new one sent no unsubscribe and the reply went on over the socket. Before the fix such a reply kept its dispatch state until the 60-minute limit (other socket messages kept it from going idle), the bar showed "Waiting for your request", and the saved chat opened later showed Req 1 with Out Unknown. Now, while the page is at the local address (`isProvisionalChatgptRoute` in `packages/capture-core/src/routes.ts`, shared with the content script), the socket's unsubscribe reply for the topic of a reply still generating stops that reply (`unsubscribeStops` in `ChatgptSession.socket`), so it ends `cancelled` with output 0 and Details lists "Stopped reply not estimated". Only the reply whose topic it names is stopped, and only before the turn's end item: the page also leaves the topic after a normal end (`done`, then the same unsubscribe reply, as in `chatgpt-socket-handoff.test.ts`), when an async job or images may still be pending (`turnEnded` in `ChatgptSession`). At a saved chat's address the unsubscribe changes nothing. The content script also treated the move from `/` to the local address as a new navigation, so no display of the reply showed there (the reply waited, bounded, for the move to `/c/<uuid>`, which a stopped chat never makes). `followChatAddress` in `entrypoints/content.content.ts` now keeps that move in the same navigation while the reply of the send is selected: the reply stays selected, its displays show at the local address (live figures while a new chat's reply runs, and Req 1 with "Stopped reply not estimated" after a Stop), its bounded promotion still waits for the chat's own address, and its figures are kept through that move. Checked live on 19 October 2026 with the rebuilt downloads (e60340fc, test Chrome): a new chat stopped 2.8 s after sending stayed at the local address and the bar showed Req 1, In/Out about 16/0 and Unknown electricity, carbon and water, with "Stopped reply not estimated" in Details; the chat opened again from the sidebar showed the same figures and no "Earlier messages not estimated". Not checked live: leaving a running new chat for another saved chat (the sidebar click failed in the probe). Tests: `chatgpt-local-stop.test.ts`, `conductor-content.test.ts` ("stopped on its local address"), `routes.test.ts` (capture-core).

*Stop before ChatGPT answered the send (20 October 2026).* In a new chat ChatGPT can show its Stop button (`button[aria-label="Stop"]`, no test id) before the send is answered: 0.46 s after the send in one of three live runs (test Chrome, d92082ab), while in the others it appeared only after the hand-over, where the rule above applies. A trusted click on it made the page cancel the send at once (`cancelStream`, `AbortController.abort()` without a reason). The send's fetch rejected with an `AbortError` 0.15 s after the click, with no response, and nothing else was sent: no `stop_conversation`, and with no topic yet no unsubscribe. The page was still at `/` and moved to its local address 1.5 s later. The capture had no topic and ended as a reply not read to its end (`capture_interrupted`), so the request was not counted as stopped. Now the capture runtime counts trusted clicks on ChatGPT's Stop control (`CHATGPT_STOP_CONTROL` in `lib/capture-runtime.ts`; only a count and a time are kept). A new chat's send that fails as an abort before its stream named a topic, with such a click after the send began and at most 2 s before (`stoppedBeforeTopic`), ends `cancelled` with output 0 (`ChatgptSession.stoppedBeforeAnswer`), and Details lists "Stopped reply not estimated". When the abort arrives before the send was read, the capture waits for its dispatch and then ends the same way. An abort without that click (the page leaving or aborting for its own reasons) and a lost connection (a `TypeError`) stay a reply not read to its end. Signed-out sends keep their `stop_conversation` rule. Tests: `chatgpt-local-stop.test.ts` ("stopped before ChatGPT answered the send", "without a trusted click on Stop").

The page world sends `GET /api/organizations/<org>/chat_conversations/<id>?tree=True&rendering_mode=messages&render_all_tools=true&include_inline_comparison=true&consistency=strong` with the page's cookies and no page headers (organization from the page's own API requests, else the `lastActiveOrg` cookie), checks the JSON names this chat, and hands an unread copy to the ordinary history reader. At most one read per navigation; a chat read successfully or not found is not read again for 5 minutes; 401, 403, 429 and 5xx pause own reads for 5 minutes, or for as long as a 429 or 503 asks in its `Retry-After` header (delay seconds or an HTTP date, up to 24 hours, `retryAfterMs` and `httpOutcome` in `lib/own-read-page.ts`; since 17 October 2026), and the pause reaches the site's other tabs. A network error, time-out, 429 or 5xx is tried once more in the same navigation, 60 s or more after the failure and after any pause it started, and only while the tab is visible (a hidden tab waits until it is shown); every other failure is final (owner decision of 14 October 2026). A failure leaves "History not loaded" and names the reason in Details. A page read of the chat during the wait or the request cancels it. When the history reader refused the page's own read ("History update problem"), the content script asks once with `rejected: true`; the page world then reads even though the page just did, unless its first request is the same as the page's (same path, query apart from `_reqid`, `bl`, `f.sid`, `hl`, `rt`, and the same `f.req`), and a chat over the history limits is not read again. The same scheduler and page-world runner serve every tool; each tool's request is in its own `lib/<tool>-own-read.ts` (sections 4.1 to 4.6). While a read runs, Details shows "Sending request", then "Receiving data", in its bottom line; the bar never shows it.

*Own read safeguards (review of 14 October 2026).* The content script hands the page world one private `MessagePort` when it starts (`{ channel, connect: true }`, `isOwnReadConnect`); the page capture takes it in a capture-phase listener added before any page script and stops the message there, so page scripts never see it. Read requests travel only over that port, each with its own answer port; a request posted on the window is ignored. When the content script stops waiting (`unanswered`), it posts `{ cancel: true }` on the answer port and the page world stops the read: no further request and no further answer reaches the history reader. Every body, including ChatGPT's session, is read inside the request's 30 s limit with a byte limit (`ownReadByteLimit`: the history reader's 16 MiB for Gemini and NotebookLM, whose bodies it decodes whole, 32 MiB for the streamed sites); a larger body is cancelled at once and ends the read as `too_large`, named in Details. A stopped or timed-out read answers at once and frees the page for the next read. The page world limits provider requests, not reads: 60 per 5 minutes per tab, and a read that reaches the limit waits (reporting progress) instead of failing, so ChatGPT's batches of 20 pages are paced. Each request after the first reports progress, so a long request never runs out the content script's wait. A page read the XHR reader turned away unread (busy slots, `rejected`) neither stops a running own read nor counts as the page's read. Details names every outcome: a chat within its 5-minute cooldown (read, not found, refused or too large), a page read, a navigation and a read the page made unnecessary; a read held by a pause is made once when the pause ends. The scheduler's `sharedPause` store makes a 429 or 5xx in one tab pause the site's other tabs; the background keeps the time in `browser.storage.session` (`lib/own-read-pause.ts`, message `own-read-pause`) and trusts a stored time only up to 24 hours ahead, the longest pause a `Retry-After` can start. A tab asks for the shared time with each request, and since the read goes out right after the grace period, the scheduler waits for that answer (with the setting's) before it sends, so a pause another open tab started holds the read (review of 18 October 2026). Tests: `own-read.test.ts` (the 14 October review cases), `chatgpt-own-read.test.ts` and `notebooklm-own-read.test.ts` (progress, paced batches).

*Load full chat history automatically (owner decision of 17 October 2026; name and help text of 18 October 2026).* The own read is a setting, on by default, with a main switch and one switch per site: ChatGPT, Claude, Claude Cowork, Gemini, Perplexity and NotebookLM. With it off the tracker still counts everything the site loads by itself; the switch only decides whether the tracker fetches messages the site did not load. Cowork has its own switch although its read runs in the claude.ai scheduler: its sessions are told apart from chats by their id (`ownReadSettingKey`). Stored in the ledger's settings record (`policy` store, key `settings`) as `ownRead` and `ownReadSites`; absent fields, as in every installation from before the change, read as on (`ownReadSettings` in `lib/own-read-settings.ts`), and a new installation stores them explicitly. The content script's scheduler is the only entry point of an own read (every provider request in the page world starts from a read it posts, and the lost-reply read goes through it too), so it is the one gate: it asks the background (`own-read-setting` with the switch, answered by `Coordinator.ownReadSetting` for the sender's own site only) right before each read it hands to the page world, and an unreadable answer sends nothing. When the switch is off nothing is requested, the bar shows what it shows when the read cannot be made ("No figures yet" or the figures read so far), and Details adds "Full chat history is not loaded automatically" with what works instead (`ownReadOffStatus` in `lib/details-overview.ts`): Reload page on Claude, Cowork, Gemini and NotebookLM (once, when no other entry offers it), "Scroll to the first message to count it" on a partly loaded ChatGPT chat, nothing on Perplexity, and a button "Turn on Load full chat history for <site>" that opens Settings (`open-settings`). Saving a change that alters any switch makes the background send `footprint-own-read-setting` to every provider tab (`notifyProviderTabs`); the tab asks again, a running read whose switch is now off is cancelled in the page world at once, and a read the switch held is made once it is on. A long read also asks again with each progress report, in case the notice did not arrive. Perplexity Computer file downloads (`fetchFile`) do not depend on the setting. Tests: `own-read-settings.test.ts`, `details-overview.test.ts` ("Load full chat history off"), `dashboard.test.tsx` ("Load full chat history"), `conductor-content.test.ts` ("Load full chat history").

### 4.5 Gemini (gemini.google.com, including /u/N/ accounts)

**Live reply.** XHR `POST .../BardChatUi/data/assistant.lamda.BardFrontendService/StreamGenerate`, framed as Google batch lines (`)]}'` prefix, length-prefixed JSON). In each inner frame:

- `inner[1]` = `[c_ chat id, r_ turn id]`;
- `inner[42]` = the label of the chat's mode (for example "3.6 Thinking");
- `inner[4][0]` = the candidate: `[0]` reply id `rc_` + 16 hex, `[1][0]` cumulative answer text, `[37]` thought summaries, `[12]` tool entries, `[30]` documents (Canvas, Deep Research).

The stream ends normally also when the user stops a reply; Gemini sends no stop signal, so a stopped reply completes and counts what it produced (adapter rule of 16 September).

**Live reply since 19 October 2026: the session channel.** A new chat (and its follow-ups) no longer sends StreamGenerate; the tracker saw no live reply and the bar showed "Tracking problem (reload page)" (`capture_hook_missing`) until the saved chat was read. Traced live that day with a passive XHR tap in the test browser on one new test chat and one follow-up in it (structure only; raw captures stay outside the repository):

- The page opens a WebChannel session on `https://geminiweb-pa.clients6.google.com/v1/processSession` (another origin, XHR, `Content-Type: application/x-www-form-urlencoded`). A first POST (`VER=8&RID=..&CVER=22&X-HTTP-Session-Id=gsessionid&$httpHeaders=..`, body `count=0`) answers `<length>\n[[0,["c","<SID>","",8,15,30000]]]`. A long-poll GET (`gsessionid, VER=8, RID=rpc, SID, AID, CI=0, TYPE=xmlhttp`) then carries the replies; further POSTs (`VER=8, gsessionid, SID, RID, AID`) carry `count=N&ofs=K&reqI___data__=<base64 protobuf>`. One session per send; the page opens it while the prompt is typed.
- The page posts three messages per send: the setup at `ofs` 0 (field 1; a follow-up names its chat at `1.8.5.1.72.1` and the previous turn's token at `1.8.5.1.72.8`, but not the previous reply or turn id), the prompt at `ofs` 1 (field 2, text at `2.9.1`) and, after the reply, a close (field 4). Then it aborts the GET.
- The GET's frames are `<length>\n<json>` (the length counts the JSON only) with `[[id, ["<base64 protobuf>"]]]` or `[[id, ["noop"]]]`. A reply message is `.2 {1 sequence, 7 {1 {1 last-frame flag, 2 {1 turn id}, 4 {4 frame}}}}`.
- The frame is StreamGenerate's JSON frame in binary: each field number is the old array position plus one. Ids `[c_, r_]` at 2 (the first frame names the chat with an empty turn), candidates at 5 (reply id at 5.1, cumulative answer at 5.2.1, status at 5.9.1 going from 1 to 2, thoughts at 5.38, tool data at 5.13, documents at 5.31), the label at 43 ("3.8 Thinking" on 19 October). The last-frame flag is 1 on the frame whose candidate status is 2. After it come the chat title (field 11) and the turn's token (field 26), which the next send's setup names. Frames also carry the page's coarse location (field 6) and a classification score table (field 25); neither is read or kept.
- The answer arrived in one or a few cumulative frames; a reply that ran code put tool steps, not thought text, at 5.38 (a JSON frame of that shape left the reply partial too). Thought text itself was not seen on this transport on 19 October.

How it is read: `lib/gemini-channel.ts` wraps the XHR open and send (installed before the history reader's wrapper, so that one stays outermost), passes every request through unchanged, reads the setup, prompt and close from the page's own posts and reads the GET's text on every `readystatechange` and `progress` event (the page aborts the GET right after the last frame, and an aborted XHR has no text left). `packages/adapters/src/gemini-channel.ts` turns the read fields back into StreamGenerate's JSON layout (`geminiChannelReplies`, `geminiChannelSend`, `geminiChannelRequestBody`), and the capture runs through the same `liveXHR` start, `GeminiDecoder` and `GeminiSession` as a StreamGenerate send, so the record shape, linking and estimates are unchanged. The reply completes at the last-frame flag; a close or a GET that is not reopened within 5 s (`GEMINI_CHANNEL_REOPEN_MS`) before it ends the reply as stopped, with the text received. A follow-up's parent is the reply whose token the setup names when this page saw that reply, otherwise the token itself, which keys no context, so the context stays unknown instead of starting a new chat. Tool data and documents with text are not read from this format (their binary layout was not seen): the reply is "Partly measured" in Details and those parts count from the saved chat. Thought text, if Gemini sends it, is read as the JSON reader read it (`[37][0]`), in either of the two binary layouts it can take. ## 6. Known limitations

- **Fetch coverage behind another wrapper (12 October 2026).** ChatGPT, Claude and Perplexity load the Datadog RUM script, which wraps `fetch` after the tracker and forwards to it, so the tracker's own wrapper is no longer `window.fetch`. `lib/capture-coverage.ts` then checks coverage passively: every finished same-origin generation request in the browser's Resource Timing list (read with a `PerformanceObserver`, because the stored list stops at 250 entries and claude.ai reaches that) must match one the tracker's wrapper forwarded. The readiness state is `direct`, `monitored` (another wrapper, nothing missed), `missed` (a request skipped the tracker: a current `capture_hook_missing` problem until reload) or `unverified` (no observer, an input whose address could not be read safely, or Gemini's XHR not direct). Details shows the coverage note only for `unverified`. Requests from iframes and workers are outside the page's timing list and are not checked. Verified live on all three sites: `direct` until the script loads, then `monitored`, and still `monitored` after a reply. Tests: `capture-coverage.test.ts`, `capture.test.ts` ("outer fetch wrapper is monitored", "watchdog: a missed request"), `conductor-content.test.ts` ("monitored wrapper").
- **History size limits (14 October 2026).** Saved messages now have the live limits (`HISTORY_LIMITS` in `packages/adapters/src/history/types.ts`): 2,097,152 characters per text field, 4,194,304 per message, 4,096 content blocks per reply; an attached file keeps the counter's 262,144 characters. Before, a field stopped at 262,144 characters and a reply at 256 blocks, so a long reply with code counted live but not from history, with no reason given. A part past a limit is left out and the message names `capture_limit_exceeded`, which Details explains under "Not included". The page's own reads of Claude, ChatGPT and Perplexity are parsed as they stream and have no byte limit; Gemini and NotebookLM bodies are decoded whole and stop at 16 MiB (`wholeResponseBytes`, "History too large"). Measured on a laptop (Intel Core Ultra 7 258V, Node 24, streamed reader plus the content script's batch check, token counting excluded): a synthetic 4.9 MiB Claude chat of 200 messages in about 40 ms with about 16 MiB peak heap growth, a 1.9 MiB ChatGPT page of 10 turns in 5 to 18 ms with about 6 MiB; the same as before the change, while the reply of 700,000 characters, the reply of 300 blocks and ChatGPT's reply of 600,000 characters now count. Tests: `history-size-limits.test.ts`.
- History a page never loads is counted only through the own read (section 4.2). With Load full chat history off for a site, the tracker fetches nothing there: a long ChatGPT chat stays "Partially loaded" until the user scrolls to its start, and Details says so; this is correct.
- An earlier ChatGPT page names no selected message, so it sets the coverage row's selected leaf to empty; loaded messages and totals are unaffected.
- Gemini shows a transient "(partial)" marker in the page while late results arrive; the extension's figures settle once the saved turn is read.
- Gemini videos appear only after a reload of the chat.
- **Trusted Types on Google pages (19 October 2026).** Gemini and NotebookLM enforce Trusted Types, which blocks the Function constructor in the page world. Zod 4 probes for it (`new Function("")`, caught) when the first object schema is made, to compile fast parsers; the blocked probe appeared as a console error from `content-scripts/capture.js` on every load. It blocked nothing (the probe's error is caught and zod falls back to its normal parser), so it did not cause the missing Gemini capture. `packages/contracts/src/zod-config.ts`, the first import of the contracts package, sets `jitless`, so no schema anywhere uses or probes for generated code; parsing is unchanged (extension pages forbid generated code already). Test: `packages/contracts/test/zod-jitless.test.ts`.
- Gemini's session channel (19 October 2026, section 4.5): tool data and documents (images, Canvas, Deep Research, code runs) are not read live from it, so such a reply is partly measured until its saved chat is read; thought text was not seen on it yet; a follow-up to a reply this page did not see live keeps its context unknown.
- NotebookLM saved chats are imported since 14 October 2026. A saved answer keeps none of the live reply's ids (checked live on 16 October 2026), so it links by its session and answer text since then (section 4.6); the fix was not yet checked live, and answers saved before it stay unlinked until the local records are erased. A notebook reopened in the same document is read by the tracker's own read (section 4.6), but only when the page made its chat reads earlier in the same tab.

- Cowork sessions never opened in this browser are not counted (decision).
- The archived original method (`packages/estimator/src/engines/original.ts`, test-only builds) still prefers the live model of a linked reply over the saved one, so for a linked Gemini tool turn its raw result can name the mode label while the selection names the saved model. It is kept unchanged for reproducibility (Codex review of 5 October, not accepted for that reason); the shipped EcoLogits engine uses `linkedReplyModel`.

A file a later entry lists again under the same `root_asset_id` counts only in the first reply of a read that lists it; whether a follow-up that edits a file lists it again was not seen live. Other file types are not counted. Files attached to a Perplexity prompt are not counted as input.
- **A parser fix that lowers a count does not correct records already stored.** A saved reply that is read again is merged with the stored one (`mergeHistoryEvidence` and `refineHistory` in `packages/contracts/src/index.ts`): a reread with fewer tokens, or with media that does not cover the stored media, keeps the stored state, because a stale or partly loaded page must never shrink a correct count. ## 7. How the data was traced

Safety rules for every probe (owner rules; keep them):

- Inspect only authorized test traffic on the owner's test accounts. Log structure, counts, lengths, field indexes and model labels only, never message text, tokens or cookies. Keep raw captures out of the repository. Never print values that contain account ids (for example ChatGPT `async_source`).
- Every test chat and message is logged in the local `TEST-ARTEFACTS.md` before it is sent; test prompts start with "AIFT test".
- Never delete chats or notebooks, never sign in or touch credentials, never accept terms for the owner.

Methods that worked:

- **Page taps.** A `window.fetch` or `XMLHttpRequest.prototype` wrapper installed from the browser automation, storing bodies in a page variable and returning only a structural summary (types, lengths, indexes, id prefixes). For Gemini install it on a fresh `/u/N/app` document, then open the chat from the sidebar. Perplexity keeps a cached fetch reference, so tap `TextDecoder.prototype.decode` for its stream.
- **Provider bundles.** The public JavaScript bundles list event names, block types and endpoints (for example Claude's `case"..._delta"` names).
- **Reading the bar.** The bar is a closed shadow root, but `window.find('Details', true, false, true)` finds its text; then collapse the selection and extend it backward by lines. Details opens with a real click at the right edge of the host element `[data-ai-footprint="information"]` (x + width − 30, middle, in CSS pixels); the tab must be visible. Reload the page to close Details (it keeps focus).
- **Hidden tabs.** Screenshots, typing and menus fail in hidden tabs. `document.execCommand('insertText', ...)` works in hidden ChatGPT and Claude tabs; Gemini needs a visible window.
- **Media.** Video and audio lengths were read by fetching the file in the page and parsing MP4 boxes or AAC frames; scene counts by decoding with WebCodecs.
