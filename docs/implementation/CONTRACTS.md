## 1. Trust and collection boundaries

The product observes supported consumer websites in an enabled Google Chrome, Microsoft Edge or Mozilla Firefox desktop profile. Personal mode stays local; an explicitly enrolled organization profile sends the permitted numerical observations to its company. It is not a developer-API proxy, billing meter, verifier of corporate authority or data-center electricity meter.

| Boundary                            | Allowed data                                                                          | Forbidden behavior                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Page MAIN world -> isolated adapter | Whitelisted protocol fragments and page lifecycle signals needed for counting         | Extension credentials, company secrets, arbitrary privileged commands                                           |
| Adapter -> offscreen tokenizer      | In-memory text, canonical model evidence, job/revision IDs                            | Persisting text, exporting text to external counting APIs                                                       |
| Adapter/worker -> ledger            | Numeric measurements, enumerated metadata, opaque identities, sanitized failure codes | Raw text, titles, filenames, document bytes, raw URLs, response bodies                                          |
| Extension -> company API            | The strictly typed observations below, credentials, policy acknowledgement            | Prompts, answers, visible/hidden thinking text, retrieved passages, content hashes, provider account identities |
| Server ingress -> abuse limiter     | Keyed hash (HMAC) of the connection address with recent request times, deleted one day after the last request | Storing or showing raw addresses; network observations (written only while IP collection is on, section 8) |
| Company API -> member               | Their own totals; privacy-filtered company totals                                     | Other user/device identifiers, IPs, per-user company breakdowns                                                 |

Page-originated data is untrusted, even after a channel nonce is checked. Validate message shape, allowed site, active frame/document, rate, size and event correlation. Nonces prevent accidental cross-talk, not malicious code on the observed page. Never render captured strings as HTML. The extension can provide useful observational analytics, not tamper-proof employee auditing: a user or compromised page can disable, spoof or evade observation. Surface provenance and health instead of claiming attestation.

Generate per-browser manifests and request only capabilities proven necessary on that target. The Chromium candidate uses `storage`, `alarms`, `scripting` and `offscreen`, with narrowly scoped host permissions for the four supported sites. Firefox must not inherit an unsupported Chromium permission; its background host, capture mechanism and permission equivalents are verified in Phase 0. Request the configured company HTTPS origin through the target browser's verified optional-host-permission flow at enrollment; declare the necessary optional HTTPS pattern but grant only that origin. Validate redirect destinations; do not send credentials across origins. No production `debugger`, `cookies`, `history`, broad installed-site access, third-party IP lookup or remote executable code. The development recorder is a separate tool/package, excluded from all store builds.

Pin a supported minimum independently for Chrome, Edge and Firefox during Phase 0. Chrome 116 is the initial Chromium design reference, not an asserted Edge/Firefox equivalent. Test each declared minimum and current stable in actual browser binaries at release; include Firefox ESR only if explicitly added to the verified support matrix. Record desktop operating-system coverage. If dependencies or APIs force a higher floor, change that manifest and compatibility tests together. Bundle tokenizer code, WASM and assets; document each target's required extension CSP. Data-only coefficient updates cannot introduce JavaScript, WASM, remote imports or executable expressions.

### 1.1 Browser-platform interface

Shared capture, tokenizer, ledger, estimator and sync code depend on a platform interface, not a global Chromium-only API. Define `startBackgroundCoordinator`, `ensureTokenizerHost`, `scheduleSync`, `registerCaptureBridge`, `requestServerOrigin`, `openDashboard` and `getRuntimeCapabilities`. Chromium uses the verified service-worker/offscreen combination; Firefox uses the packaged background/worker mechanism demonstrated in Phase 0. Both implement the same numerical/message schemas and durable recovery rules. No hidden raw-text persistence or website-visible tokenization tab is an acceptable fallback. A missing critical capability blocks enrollment/measurement with a clear supported-version message.

Store packages can have different extension IDs/origins and signing/update mechanisms. Configure authenticated company enrollment and allowed extension-origin handling for each package; do not hardcode a Chrome store ID as a user/company identity or bypass server authentication based on extension origin. Keep server tokens and company identity independent of browser/store. Verify credential isolation, host permission grants, page-world isolation and update behavior on all three targets. Browser migration creates a new installation paired to the existing pseudonym, not a raw transfer of another browser's credentials.

## 2. Identity and stable keys

**Current role/brand amendment:** use [Resource Gauge + Fern and the two-role contract](BRAND-ROLES-AND-DESIGN-HANDOFF.md). Organization roles are exactly `user`/`admin`; email OTP is the only organization login factor. Platform-owner authority is separate. Legacy prose using “member” means the ordinary `user` role, not an additional role.

Organization email OTP delivery uses Brevo under [the privacy-first setup requirements](BREVO-PRIVACY-SETUP.md). The [product/enrollment contract](PRODUCT-AND-ENROLLMENT-SPEC.md) defines registration, administrator login, the extension's email-code connection, email canonicalization and how the organization is found from the work email domain. Email belongs in a separate authentication boundary, not usage events; personal-only mode has no email/Brevo dependency. Domain match never grants administrator privileges.

### 2.1 Tenant identity and stable observation keys

- `company_id`, `user_id`, `device_id`: random UUIDs assigned by the server. Device means one enrolled browser profile, not a physical machine. Store an allowlisted `browser_family` (`chrome`, `edge`, `firefox`) on installation enrollment for compatibility/admin display; this is declared installation metadata, not trusted identity evidence or a full user-agent fingerprint. The authenticated principal determines company/user/device; ingestion bodies cannot select another user.
- One profile has one active organization enrollment. A unique verified canonical work email within that tenant retrieves one stable user ID. Store encrypted email/lookup mapping separately; numerical IDs do not make the linked usage anonymous. Personal mode has a random local identity/namespace and no server membership. Never merge by IP, language, browser fingerprint, matching conversation text or a common email across different tenants.
- Pairing means verifying the same work email with an email code in the extension, which finds the same tenant, and confirming a new installation-bound connection there. It works between Chrome, Edge and Firefox on one computer or several, without an existing device or recovery phrase. Three installations yield one user ID and three installation IDs, not proof of three physical machines. Distinct genuine requests remain distinct; only verified replay/duplicate observations are deduplicated. Reinstalling and re-verifying the same identity does not silently create another user or revoke healthy installations.
- `request_id`: UUID generated and durably saved on the initiating device for one dispatched user action. It remains the same across progress revisions and observed internal retries.
- `attempt_id`: UUID for one observed transport/generation attempt. Each attempt has one originating request; execution evidence determines whether it contributes to **observed generation attempts**. Additional request associations are allowed only through the explicit reconciliation rules below. Multiple transport reconnects are not multiple executions.
- `revision`: positive integer, increasing independently per request/attempt. Only the originating device revises its record. A different device can retrieve canonical results, but does not fabricate revisions for imported history.
- `conversation_key`, optional `provider_request_key` and optional `provider_attempt_key`: lowercase hexadecimal HMAC-SHA256 outputs. Compute inside a trusted extension context over a length-prefixed tuple of key version, site, identifier kind and the whitelisted stable provider IDs observed in Phase 1. Do not hash prompt text, URLs or titles. A request key is valid only if its source identifies the user dispatch, not merely a conversation/message ancestor reused for regeneration. NotebookLM notebook guides (W9) are the one exception, because the provider gives no id for them: the page reads a notebook's saved guide again the first time the notebook opens in a page, and the only id in the response changes with every call (5 October 2026). Their request key names the notebook's guide request, one per notebook (guides count no request), and their attempt key names the guide by a 64-bit digest of the notebook id and the guide's generated text, keyed like every other key, so a read of a saved guide aliases to the first and a guide with new text is a new attempt. The HMAC secret is random per company/user and shared only with authenticated paired profiles. Keep the server copy encrypted for authenticated pairing/recovery; record key version and do not rotate without a key migration. Company deduplication (W11, 4 October 2026) does not use this per-member secret; it uses one key per company, described in section 5.2.
- Raw provider IDs may exist in a local mapping store, never in upload bodies or logs. Temporary chats without stable identifiers use a random persisted conversation key and `conversation_identity_local_only`.
- If no stable generation identifier is available, keep the local UUID and `cross_device_dedup_unverified`. Do not advertise cross-device exact deduplication for that mode. Observing the same remote conversation on another device is history synchronization, not new usage.

A shared conversation key allows a paired device to fetch previously recorded conversation totals. When offline, the bar shows only this profile's recorded subtotal and explicitly says so. It does not manufacture the other device's records from rendered history.

### 2.2 Organization login, connection and credential protocol

**13 October 2026 amendment (owner decision):** the hosted service has one address, `https://aifootprinttracker.com`, and every hosted organization is served there. The organization is found from the verified work email domain. Members connect only in the extension with an email code; there are no per-organization subdomains, no member web sign-in and no web approval of a browser connection. Only administrators sign in on the website. A self-hosted server keeps one organization at its own origin. The [server integration notes](../../apps/server/API-INTEGRATION.md) describe the implemented contract and take precedence where this section is less exact.

1. The same signed store package supports personal and organization modes. The website distributes the normal package, not an embedded company/admin credential. Installing alone does not enroll or upload old personal history.
2. The user starts Connect in the extension and enters a work email. The extension uses the hosted origin `https://aifootprinttracker.com` unless the user opens the secondary "Your organization runs its own server?" option and enters that server's exact HTTPS origin. It requests only that origin's verified permission and calls `POST /v1/connections/otp/request` with the email and a dispatch ID. The server sends one `connect`-purpose Brevo code. At the hosted origin it selects the organization whose registered work domain equals the email's domain; a self-hosted server uses its one organization. A free-mail domain is refused at once with `work_email_required`. Otherwise the response does not depend on whether an organization uses the domain, so it cannot reveal which domains are customers. No email, code or usage credential is sent to the AI page.
3. The user enters the six-digit code in the extension. The extension creates a random 256-bit verifier and calls `POST /v1/connections` with its SHA-256 challenge, the challenge ID and the code. The server checks the code (five attempts, expiry, single use), retrieves or creates the stable membership as `user` (capacity enforced) and creates a ten-minute connection in state `verified`. Only after a correct code may it answer `organization_not_found`; a suspended member gets `member_unavailable`. A person whose records were erased joins again as a new membership with nothing of the old one, and a browser whose person was erased connects as a new browser (owner decision of 22 October 2026). The response names the organization (`company_name`, public `company_origin`) and carries its current policy so the extension can show what is shared.
4. The extension shows "Connect to {organization}?" with the collection disclosure. On confirmation it claims the connection with `POST /v1/connections/exchange`, its private verifier, a persisted exchange ID, the `policy_version` it showed and `disclosure_acknowledged: true`. A policy changed in the meantime returns `policy_changed`. A public connection ID alone cannot claim credentials. Store the acknowledgement, device creation or permitted same-installation renewal, and consumed state transactionally; enforce tenant, policy, expiry and active-user checks.
5. Exchange returns a 10-minute opaque access token, rotating refresh token, the organization name and user-scoped key material. New installations also receive a narrowly scoped reconnect proof stored only in trusted extension storage; this is not a user-managed recovery phrase and grants no access without a fresh email code from the member who owns that installation. Store only hashes except the encrypted idempotency cache. The product specification's Section 5.4 renews the **original device ID** when that same installed profile resumes an old queue, with proof rotation and preservation of valid earlier enrollment eras. Reinstall after storage loss creates a new device for the same user, not permission to revise the lost device's records. Trusted storage restrictions are verified separately in Chromium and Firefox; page/content scripts never receive credentials.
6. Refresh tokens expire after 30 days of inactivity, rotate on use and support reuse detection. The client uses a persisted refresh operation ID. For an identical operation ID, return the same encrypted cached rotation result for up to 2 minutes after a lost response; reuse with a different operation ID revokes the token family. The server never blindly accepts an old token as current.

Website sign-in (`POST /v1/auth/otp/request` and `/verify` with purpose `login`) is for administrators only. An active administrator gets a host-only web session and the destination `/admin`; anyone else gets `admin_required` with no session and no new member. At the hosted origin the code is sent whether or not an organization uses the email domain, and `organization_not_found` comes only after a correct code. One consumed OTP is never redeemed again for another session.

Connection exchange requires a client-generated persisted `exchange_id`. Redeem the verified verifier-bound connection and store an encrypted result bound to its proof/exchange ID in one transaction. An identical authenticated retry can retrieve the same result for 24 hours after exchange unless revoked/deleted; this does not extend token expiry. A different exchange ID cannot redeem a consumed connection. Persist credentials before discarding client exchange state. After that recovery window, offer normal same-email reconnection and installation cleanup; never silently create another user. Full connection, cancellation and lost-response state machines are defined in the product specification.

Each device also receives an independent random deletion-receipt credential. Its hash is stored separately from usage and reconnect credentials and it can only retrieve/acknowledge signed erasure instructions for that device. It cannot read usage, enroll, reconnect, refresh, or upload. This narrowly scoped channel remains usable after full-user deletion revokes usage access; see Section 9.

Do not put connection verifiers, OTPs, access/refresh credentials or secrets in URLs, DOM messages, analytics, referrers or screenshots. The connection flow runs entirely in the extension and opens no verification page, so no connection identifier needs to appear in a URL. Authentication and connection endpoints are rate-limited independently of usage ingestion. Personal mode never calls these endpoints unless the user explicitly starts Connect.

## 3. Canonical observation model

### 3.1 Common scalar types

| Type             | Contract                                                                                                                          |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `Instant`        | ISO 8601 UTC timestamp ending in `Z`, millisecond precision                                                                       |
| `Counter`        | Nonnegative base-10 integer string, no exponent/sign/leading zeros except `"0"`; individual measurements <= signed BIGINT maximum |
| `Decimal`        | Nonnegative fixed-point decimal string, no exponent, NaN or Infinity; precision <=38, scale <=18                                  |
| `Site`           | `chatgpt`, `claude`, `gemini`, `perplexity`                                                                                       |
| `CanonicalModel` | Registry identifier from the accepted bundle or null; arbitrary page/model display strings are not uploaded                       |
| `Version`        | Explicit schema/adapter/tokenizer/method version; unknown values are not coerced to current                                       |
| `ReasonCode`     | Allowlisted enum in the failure/coverage catalog; no arbitrary exception message                                                  |

Numbers in JSON are used only for bounded structural values such as revision and page size. Token totals use strings to avoid JavaScript precision loss. Python Decimal and a pinned decimal implementation in TypeScript perform resource arithmetic. Database totals use sufficient NUMERIC precision; overflows are errors, not saturation. Round for display only.

Every request observation contains exactly:

| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `request_id`, `revision`          | UUID, positive integer                                                                                                                                                                             |
| `conversation_key`, `key_version` | Opaque stable/local key and its derivation version                                                                                                                                                 |
| `provider_request_key`            | Optional verified opaque dispatch identity for deduplication; null when unavailable                                                                                                                |
| `site`, `adapter_version`         | Site enum, packaged adapter version                                                                                                                                                                |
| `action`                          | `send`, `regenerate`, `continue`, `edit_and_send`, `read_aloud` (speech made from a reply already shown; its energy counts, but it is not counted as a request)                                     |
| `dispatched_at`, `ended_at`       | Instant; terminal timestamp nullable                                                                                                                                                               |
| `state`                           | `dispatched`, `generating`, `completed`, `cancelled`, `failed`, `interrupted_unconfirmed`                                                                                                          |
| `model_id`, `model_evidence`      | Canonical model or null; `response_field`, `request_field`, `ui_selection`, `unknown`                                                                                                              |

The authenticated device association and server receipt time are added server-side (and a network observation ID while the server has IP collection on, section 8). Request counts derive from request records, not their `features` or number of attempts.

### 3.4 Per-field measurement object

Every token field is present as an object with:

- `value`: Counter or null.
- `evidence`: `provider_reported`, `official_tokenizer`, `calibrated_estimate`, `heuristic_estimate`, `unknown`, `not_applicable`.
- `scope`: `provider_request`, `observed_text`, `reconstructed_context`, `provider_defined_subset`.
- `completeness`: `complete_for_scope`, `partial`, `unknown`.
- `profile_id`: nullable tokenizer/normalization registry profile.
- `reason`: nullable allowlisted reason.

An official tokenizer gives an exact count for the supplied text under the pinned encoding, not a guarantee that the browser saw every token consumed by the cloud service. `provider_reported` means the provider exposed a value with verified semantics, not independent physical verification. `not_applicable` has null value and a reason. A numerical zero is valid only when the relevant component is known to be zero.

Required token field names and relationships:

| Field                                       | Meaning and aggregation rule                                                                                                                                   |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `new_input_text`                            | Newly supplied observable user text; excludes prior context. Preview is not usage.                                                                             |
| `logical_input_total`                       | Full request input according to verified provider semantics, or explicitly reconstructed context. Unknown if reconstruction is unjustified.                    |
| `input_uncached`                            | Verified uncached subset, if exposed                                                                                                                           |
| `input_cache_read`                          | Verified cached-read subset, if exposed                                                                                                                        |
| `input_cache_write`                         | Verified cache-write subset, if exposed                                                                                                                        |
| `answer_output`                             | Generated answer text under its reported/tokenized scope                                                                                                       |
| `visible_thinking`                          | Tokenized visible thinking or thinking summary; scope must say which through the profile                                                                       |
| `reported_reasoning`                        | Provider-reported reasoning tokens, if exposed; not inferred from summary length                                                                               |
| `output_total`                              | Verified aggregate output, or an explicitly scoped estimate without overlapping parts                                                                          |
| `tool_input`, `tool_output`                 | Separate observed tool-related token quantities; not automatically additional model input/output                                                               |
| `image_input_tokens`, `image_output_tokens` | Verified provider/model-specific image-token quantities or scoped estimates; null with reason when unavailable, never plain-text tokenization of binary images |

Normalization profiles explicitly declare whether reasoning/cache/tool fields are inclusive, exclusive or overlapping. For example, sum disjoint cache input categories only if that provider's observed schema proves they partition logical input. If output total already includes reasoning, never add reasoning again. Visible thinking may be a summary of hidden reasoning: do not substitute it for hidden reasoning or add both by default.

The compact bar uses logical input/output totals when meaningful. Otherwise it displays the available observed-text subtotal with a label such as **Input text, partly measured**. Do not silently switch a metric's scope while keeping an unqualified “total” label. Full-request counts and observed-text counts are separate dashboard series; mixed-scope records are shown as separate subtotals, not one purported exact token total.

Context is accounted per generation: repeated processed history can contribute repeatedly to logical input. Conversation size (each unique visible message once) is a different diagnostic and never used as cumulative request usage. No context-window percentage, quota limit, cache timer or word-to-token rule is a provider usage field.

### 3.5 State, checkpoint and capture rules

```text
Draft preview (memory only)
    -> observed generation dispatch -> durable request + dispatch-only attempt skeleton
    -> generating -> completed | cancelled | failed | interrupted_unconfirmed
                         -> later evidence may refine the same record by revision
```

- A click without actual dispatch is not a counted request. A dispatched request that receives an error is counted with a failed outcome; resource use may be unknown.
- Dispatch-only skeletons have `execution_evidence=none` and do not increase observed-generation-execution counts. Promote only on a validated provider start signal, newly generated content or verified usage evidence. HTTP 200 or opening an SSE connection alone is not that evidence. A rejection before generation therefore yields one failed user request, zero confirmed observed generation attempts and one dispatch-only/unconfirmed transport attempt. Keep unconfirmed attempt counts visible separately; absence of execution evidence is not proof of zero backend work.
- Internal automatic retries are separate attempts only when distinct execution evidence exists. User-initiated retry is a new request. Reconnect/replayed stream chunks are revisions of the original attempt.
- Start and terminal state are persisted immediately. Numeric progress is checkpointed at most once per 2 seconds per attempt. Progress uploads are coalesced to at most once per minute; start/terminal revisions enter the next available sync batch.
- `completed` means observed terminal completion, not inferred from an idle timer. Timeout/restart without terminal evidence becomes `interrupted_unconfirmed` with known numeric progress retained. A later verified completion can refine that state.
- Observation state, token-processing state, sync state and tracking health are independent fields. A completed answer may still be awaiting tokenization, estimation or upload.
- Full captured text is re-tokenized at completion because chunk token counts are not generally additive. After a crash, a numeric checkpoint cannot reconstruct unseen text; show partial coverage. Rendered DOM recovery is a lower-evidence method and must not be upgraded to raw-stream coverage.
- Initial bounds: four concurrent stream buffers, 8 MiB decoded text per stream, 32 MiB total raw-text budget; file processing <=25 MiB input and <=8 MiB extracted text per job, one file job at a time. Streaming limits apply before unbounded response clones accumulate. At a limit, stop the measurement branch, preserve the original website request, and record `capture_limit_exceeded`. Large/unsupported documents retain count/type metadata and unknown token/resource components.
- File extraction operates only on bytes already exposed to the extension through the observed upload flow, in memory, using bundled parsers in an isolated worker. Do not fetch private files from guessed URLs. Local PDF text extraction does not prove what the provider sent to a model; OCR, image encoding and retrieval selection remain unknown unless exposed.

### 3.6 Development-only Anthropic calibration

The production extension counts locally or consumes verified usage fields from the consumer site's own responses. It does not call Anthropic's developer API, and the company ingestion service does not forward employee content to it. Employees provide no provider API keys.

Create a separate maintainer tool under `calibration/anthropic/` using an explicitly supplied development key. Allow only the counting endpoint, never automatic fallback to message generation. Run the following workflow:

1. Load the licensed synthetic/public corpus, its split manifest and the exact Claude model ID to test. Reject employee exports or runtime capture folders as calibration inputs.
2. Submit structured counting requests through the official SDK's `messages.count_tokens` method. Retain the returned input-token estimate, model/version/date, fixture ID, request shape and sanitized success/failure metadata. No API secrets enter fixtures, logs, repository or packaged artifacts.
3. Compare local candidate tokenizers using equivalent serialized content and explicitly recorded envelope/system/tool overhead. Do not assume one fixed overhead subtraction works for all request shapes. Fit/select on the training split and report performance on untouched holdout groups.
4. Version the selected approximate profile and publish numerical calibration evidence. The employee package receives only approved tokenizer assets/profile data and synthetic golden fixtures, never the API key or a remote counting dependency.
5. Rate-limit and retry transient failures; abort invalid-model/auth failures visibly. A failed/incomplete calibration cannot promote an accuracy badge. Rerun deliberately when supported model/tokenizer generations change; live calibration is not a mandatory ordinary CI or employee operation.

Anthropic documents counting as free, authenticated and rate-limited, returning an input-token estimate that can differ from actual inference usage; it does not simulate cache hits. This is a reference for our development tests, not a readout of historical Claude.ai usage. Counting answer text as a new input does not establish its original generated-output usage or hidden reasoning. Generated-output validation needs a separate approved reference dataset/experiment; no paid generation is triggered by this workflow. [Official counting documentation](https://platform.claude.com/docs/en/build-with-claude/token-counting).

### 3.7 Context-window guidance, separate from consumption

The footprint helper uses an advisory **active-context snapshot**, not cumulative conversation tokens spent. ## 4. Resource calculation contract

### 4.1 Boundaries and units

Base units: energy in kWh, emissions in g CO2e for a compatible greenhouse-gas profile or g CO2 for an explicitly CO2-only profile, and water consumption in L. UI chooses Wh/mWh, g/kg and mL/L automatically with no more significant digits than the evidence warrants. The displayed CO2/CO2e label follows the accepted profile, not a fixed suffix. Keep differently scoped gas series separate. Display an estimate marker and an expandable method/boundary explanation.

Operational boundary includes estimated serving IT, allocated facility overhead and electricity-supply impacts. Exclude training, hardware manufacturing, employee computer/network and unsupported auxiliary work. Not all operational emissions are captured by electricity alone; label the calculated carbon quantity **electricity-related CO2 or CO2e**, according to the accepted profile, and disclose excluded direct refrigerant/fuel emissions unless a compatible profile explicitly includes them.

For a profile whose starting energy is IT energy:

```text
E_facility_kWh = E_IT_kWh * PUE
C_electricity_g = E_facility_kWh * grid_intensity_g_per_kWh
W_direct_L = E_IT_kWh * WUE_IT_L_per_kWh
W_upstream_L = E_facility_kWh * electricity_water_L_per_kWh
W_total_L = W_direct_L + W_upstream_L
```

For a source already reporting facility energy, set the facility quantity directly; do not multiply by PUE again. Compute IT energy from it only if that source's compatible PUE is known. If WUE uses facility energy as its denominator, multiply by facility energy and record that definition instead of using the IT equation. Mixing incompatible denominators is a validation error. Water withdrawal and water consumption are not interchangeable.

Location-based carbon and market-based carbon are separate methodologies. Default to explicitly labeled location/scenario-based electricity factors where defensible; do not apply purchased-renewables claims as zero physical footprint. Browser/user/company IP cannot select a data-center region. Unknown region is an explicit scenario set or an unavailable factor.

### 4.2 Method bundles and results

The [methodology evidence and validation contract](METHODOLOGY-QUALITY-GATES.md) is normative. Require separate source activity period, factor-data period, publication/revision and software snapshot; GHG gases/equivalence method and generation/lifecycle boundary; water consumption/withdrawal, freshwater/all-source coverage and energy denominator. An unresolved field remains explicit. Compatibility is stricter than matching units. CO2-only factors must be labeled and scoped as CO2-only, not silently substituted into a full CO2e series. Different water-source categories require an explicit common covered scope or separate components.

Each immutable bundle contains `method_id`, schema version, semantic version, content hash, source revision/date, licenses, equation version, energy boundary, carbon boundary, water denominator, supported model/workload domain, hardware assumptions, PUE/WUE factors, geography scenarios, cache/reasoning semantics, calibration evidence, expiry/review date and signature. Private signing keys remain with the deploying operator; the extension verifies a trust key established during authenticated enrollment. Package a baseline trust/config mechanism, never accept an unsigned arbitrary URL update.

The exact baseline equations, published coefficients and source corrections are defined in [the canonical public article](../methodology/content.html). Reference profiles are not calibrated consumer-model profiles. Use the versioned four-model text cohort and 208-configuration image cohort only within their declared applicability and scope. Image per-output GPU joules are already normalized across the benchmark's GPUs/batching. A proportional environmental allocation of that component remains `gpu_associated_reference`, not complete IT or provider-operation measurement.

P0/P6 must explicitly assemble and review a runtime baseline bundle: required observations, allowed workload/modality, source coefficients, missing work, transfer/environment assumptions, coverage labels, cohort eligibility and reviewer/version/hash. This can authorize a useful **rough, unvalidated** estimate without claiming measured closed-provider accuracy. It cannot upgrade a vendor reference or research fixture into a calibrated profile. Do not import raw research registries as automatically approved runtime configuration. Keep selection values `matched_profile`, `highest_comparable`, `reference_only`, `unavailable`; a matched name is not an accuracy badge. The external published-reference catalog and SweetSpot experiment remain research-only. A usable reviewed highest-comparable text result can enter its scoped ordinary series; reference-only figures cannot. Image GPU-associated and text/IT series remain separate unless a new common partial-scope contract is reviewed.

Avoid maintaining separate untested formula implementations: the initial project-owned TypeScript kernel and Python reference share the bundle schema and golden fixtures; verify against pinned EcoLogits operational outputs in the validated baseline domain. EcoLogits remains a dependency/reference, not an excuse to label all input-aware formulas EcoLogits. A two-phase engine is a distinct method ID until its evidence supports promotion.

For every metric return:

Water returns direct and upstream components plus their sum. If one is unknown, total water is null and the known component is shown separately, not promoted to total. The same rule holds for complete-operation versus text-component energy. A known modeled subtotal is not necessarily a strict lower bound because estimation bias can be bidirectional. If no defensible finite upper bound exists, `scenario_high` remains null.

Input length, cached context and hidden reasoning can dominate error. An output-only profile is not validated for arbitrarily long context. Treat outside-domain workloads as unsupported or a clearly labeled partial/rough scenario, never silently apply a “per prompt” constant. Billing discounts do not specify physical energy discounts.

When the observed model lacks an applicable profile, select the highest electricity estimate among all eligible profiles in the same pinned modality/boundary/workload/environment cohort. Retain the selected profile's full environmental vector, not independently maximized carbon or water. Resolve ties by stable ASCII profile ID order. Record exclusions, assumptions and the cohort's finite extent; this maximum is not a guaranteed physical upper bound. The observed model identity never becomes the proxy identity. Unknown model identity or hidden reasoning alone does not force unavailability. No eligible comparator still requires `reference_only` or `unavailable`, never a cross-modality substitution.

Reject incomplete comparison signatures and conflicting factor vectors under the same immutable scenario identity. The authoritative server recomputes quantities from the accepted factor bundle; equal scenario-name strings do not validate client-supplied vectors. Published-reference catalogs with `runtime_selection_allowed=false` are not approved method bundles. Conditional Monte Carlo spread, a heterogeneous literature range and a model's empirical prediction error are distinct fields, not interchangeable uncertainty badges.

### 4.3 Aggregation of estimates

Sum only compatible dimensions and scope within the selected calculation view. Each estimate is immutable under the key `(attempt_id, observation_revision, method_id, calculation_view)` and records its observation payload hash. A corrected observation creates a new estimate row; it never overwrites the preceding revision's result. The canonical attempt points to its latest accepted observation revision and that revision's original method/result or explicit pending/unavailable status. Original-view totals select only this current contribution, not every historical result; if it is pending, the prior revision can be shown separately as dated provisional data, not as the current answer. A new method can generate a separate **recalculated view** with its own version, coverage and timestamp; it never overwrites original results silently. Method groups with incompatible boundaries are separate subtotals. For comparable methods, retain method-group breakdowns and a mixed-method indicator.

For uncertainty, sum each named coherent scenario across applicable records, then report the minimum/maximum across those complete scenarios. Do not mix a low factor from one boundary with a high factor from another, sum unrelated percentiles, call a scenario spread a 95% interval, or divide shared model bias by the square root of request count. If no common scenario covers the records, report component/method ranges separately and aggregate range as unavailable.

`reference_only=true` always contributes zero **records** to the normal estimated-usage series, not a zero footprint value. Its figure appears only in a separate benchmark-reference view. Preserve matched/highest-comparable coverage counts. GPU-associated image figures and broader IT/text figures use separate scoped subtotals unless a reviewed common partial-coverage view explicitly defines and labels their combination. Generated images aggregate from canonical attempt operations, never both request intent and attempt results. Request counts remain valid independently of resource-estimate success.

These totals are attributed estimates, not the counterfactual resources saved by removing requests. Do not label an arithmetic decrease as physical savings or use unmatched workload shares as intrinsic provider-efficiency rankings. A source median is not substituted for an expected per-request mean in projections. Display per-tool methodology/coverage differences alongside usage shares.

### 5.2 Ingestion protocol

`POST /v1/usage/batches` accepts this envelope:

```json
{
  "schema_version": "1.1.0",
  "batch_id": "00000000-0000-4000-8000-000000000001",
  "sent_at": "2026-09-07T12:00:00.000Z",
  "client_version": "0.1.0",
  "deletion_epoch": 0,
  "records": []
}
```

The empty array above illustrates envelope syntax only; production ingestion requires 1-100 records and <=512 KiB serialized UTF-8. Validate a maximum nesting depth of 16 and reject unknown fields. Requests precede child attempts in a batch. A missing parent is `dependency_missing`, retried after parent acknowledgement. A batch uses one authenticated installation and company.

Per-record transaction:

1. Authenticate and bind company/user/device from the token. Validate schema, quantities, time, revisions, policy and deletion markers.
2. Lock the canonical record and its deduplication key. Insert first revision or validate a revision of an owned record.
3. A duplicate stable provider-attempt key maps to the existing canonical attempt and returns its ID. Do not add a second contribution. Conflicting attribution/evidence is quarantined for reconciliation, not merged by token maximum.
4. Compute the authoritative estimate using the proposed accepted method. If unavailable, persist observations and an explicit pending/unsupported estimate status. Never silently substitute another method.
5. Commit canonical observation, revision history, current estimate/status, old-to-new aggregate contribution and receipt atomically. A failed transaction produces no durable acknowledgement.
6. Return individual acknowledgements after commit. Different records in the batch may succeed or fail; the envelope is not globally atomic.

**Parent-request reconciliation is part of deduplication, not an optional follow-up.** A verified duplicate `provider_request_key` aliases the later request to the existing canonical request. In the same transaction, remove any already-applied duplicate request/outcome/active-user contributions, redirect its valid children to the canonical parent and deduplicate attempts. Preserve an alias/receipt so retries cannot resurrect the duplicate. Recompute affected distinct-user/device memberships; simply decrementing a distinct-user counter is not sufficient.

When only the attempt key matches but the parent request IDs differ, do not assume the two user actions were identical. With evidence of the same dispatch, apply the parent alias transaction above. With evidence of two genuinely distinct user dispatches sharing one provider execution, retain both request counts and associate them through `request_attempt_links`; attribute the attempt's token/resource contribution once to its originating request and once in conversation/company totals, not once per link. Show that association in request details. Without evidence resolving the relationship, quarantine the later parent and its contested contributions as `request_identity_ambiguous`, keeping one canonical attempt contribution and a separate unresolved-request count. Previously applied contested contributions are removed transactionally; no current-looking exact request total hides the unresolved count. Cross-user key collisions are authorization/integrity errors, never a reason to merge users.

**Company deduplication (4 October 2026, W11; owner decisions of 30 September and 2 October).** Members of one company can see the same prompt or reply, for example on a shared provider account or in a shared thread. Each such prompt or reply counts once in period, company and admin totals:

- Key delivery: the server creates one random key per company on first use and keeps it encrypted in the company record. `POST /v1/connections/exchange` and every `POST /v1/auth/refresh` return it as `company_dedup_key` (32 bytes, base64url), so installations enrolled earlier receive it at their next refresh. A server without company keys returns none; the extension then sends no keys. A malformed key fails the exchange or refresh as `payload_rejected`.
- Browser key: an HMAC-SHA256 under the company key over the existing length-prefixed tuple of key version `1`, site, kind and the provider's own id. Kinds are `company-request`, `company-attempt`, `company-saved-prompt` and `company-saved-response`, separate from the per-member kinds. A reply uses the id behind `provider_attempt_key` (live `attemptId` or output id; saved `liveAttemptId`). A saved NotebookLM answer linked to its live reply by content takes the key the live capture made (16 October 2026). A prompt is named only for requests the user wrote (`send`, `edit_and_send`): ChatGPT and Perplexity by the message id their request carries, Gemini by the turn id of the reply's stream, Claude by the message the reply answers; saved prompts use the same ids. Saved rows no live capture sees (NotebookLM Studio items, saved replies without their live id) use their own id under the saved kinds. Regenerated replies are new replies with new keys; continued replies, read aloud, notebook guides and Cowork results get no key, so each copy counts as before (Cowork results are counted from each browser's own checkpoint, so two members' rows of one result are different measurements).
- Transport: the key never enters a record; a record's `company_dedup_key` field must be null. `POST /v1/usage/batches` may carry `company_dedup_keys`, at most one entry `{kind, record_id, company_dedup_key}` per record of the batch, and `POST /v1/me/history` may carry `company_dedup_keys` entries `{message_key, company_dedup_key}`, at most one per message of the page. Both are left out when no record or message has a key; an entry naming anything else is rejected with 422. The extension keeps each key beside its queued record or saved row and sends it only while the server hands out a company key; an upload built before a refresh that withdrew the key goes without its key list.
- Server storage and election: the server stores only `HMAC(lookup secret, "company-dedup:" + tenant, key)`, never the browser key, so a leaked company key matches nothing in a database dump or export. A recorded key never changes: a different key for the same live record, also on a retry of the same revision, is `immutable_identity`, for the same saved message a `conflict`. Among the records of one key, one wins by evidence: exact provider counts, then a complete live count, a partial live count, a complete saved count, a partial saved count, a live copy that measured nothing, a saved copy that measured nothing; then a live copy before a saved one, then the earliest (live dispatch or start, saved first observation), owner and id. The winner's owner keeps all its records as they are; every record of another owner is marked shared. Elections run after live ingest, after alias handling, after saved-history ingest and after each erased live record or saved row, so erasing the counted copy hands the prompt or reply to another member's copy.
- Totals: shared records stay out of period, company and admin totals, breakdowns, daily rollups and the restore gate's rollup check, and stay in conversation views, so a member who opens a coworker's chat still sees the chat's figures. Personal period figures follow the chosen record, so a reply measured live stays with its sender unless another member's copy has provider-reported counts; otherwise the first copy by the order above counts, for example the first member who opened a complete copy. Same-owner duplicates keep the per-member rules above. The restore gate applies the election rules to the restored records and fails (`restore_company_count_inconsistent`) when a key's stored flags count it twice or never.
- Limitations: records made before the key reached an installation carry none and are never merged; a saved copy is named when its chat is next opened and is then uploaded once more. A Claude or Gemini prompt is named from the reply's stream, so a prompt whose reply never started has no key.

Acknowledgement fields: `kind`, `record_id`, `revision`, `canonical_id`, `payload_hash`, `status`, `error_code` nullable, `retryable`, `server_record_version` and `estimate_status`. Envelope includes `batch_id`, `server_time`, `deletion_epoch` and `results`.

| Record status             | Meaning / client action                                                                                                                                                                                                            |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `applied`                 | Durable canonical record/estimate or explicit unavailable result committed; remove this revision from upload queue                                                                                                                 |
| `duplicate`               | Same ID/revision/hash already committed; reconcile to canonical version                                                                                                                                                            |
| `stale`                   | A newer owned revision already exists; never overwrite; fetch canonical record and reconcile                                                                                                                                       |
| `stored_pending_estimate` | Numeric observation durable, calculation job pending; stop reuploading this revision but keep “resource calculation pending” visible and poll normal summary/status                                                                |
| `rejected`                | Schema/quantity/unsupported-client error; retain in local quarantine with recovery instructions                                                                                                                                    |
| `conflict`                | Same revision with different payload or incompatible stable-key attribution; retain/quarantine; do not invent a new ID to bypass conflict                                                                                          |
| `aliased`                 | Verified duplicate request/attempt mapped to another canonical ID; reconcile local identities and subtract duplicate local contributions                                                                                           |
| `erased`                  | Explicit deletion tombstone prohibits this record/range; remove affected local data through the deletion workflow                                                                                                                  |
| `retention_expired`       | Effective organization retention cutoff excludes the complete request family; terminal receipt, reconcile policy and purge affected local organization records with visible counts; never relabel occurrence time or retry forever |

Same ID + revision + canonical JSON hash is an idempotent no-op. Same ID/revision with a different hash is conflict. Canonicalization uses an agreed deterministic JSON representation implemented and tested in both runtimes; no raw content is hashed. An older revision cannot replace a newer one. Final measurements may legitimately be lower than provisional ones; use signed aggregate deltas, not monotonic maximums.

Unknown method IDs persist the valid numeric observations with `stored_pending_estimate` only if they pass schema/auth/deletion/retention validation. The server schedules a bounded retry/maintenance job and exposes backlog age. Unsupported models with no plausible method are an explicit terminal `unavailable`, not an endlessly pending job. Operator installation of a compatible approved bundle triggers recalculation of pending records transactionally.

### 5.3 Transport retry rules

Use full-jitter exponential retry starting at 1 second, capped at 30 minutes; persist next eligible time and attempt count. Respect `Retry-After`. Alarms and ordinary extension activity resume eligible work after suspension. Batch progress may wait up to 15 seconds to coalesce; terminal usage is eligible immediately. Enforce per-device server rate limits with a documented 429 response, not connection resets.

| Condition                     | Required handling                                                                                |
| ----------------------------- | ------------------------------------------------------------------------------------------------ |
| Lost response / timeout / 5xx | Retry the same record IDs/revisions; show unsynced count and oldest age                          |
| 401                           | Single-flight token refresh; retry once after success; otherwise visible reconnect-needed state  |
| 403 revoked                   | Stop upload retries; retain local queue; show revoked enrollment and recovery/disconnect options |
| 413                           | Split the batch; a single oversized record enters visible quarantine, never truncated silently   |
| 429                           | Honor delay with jitter; retain records                                                          |
| Invalid envelope              | Display schema/client error; retain complete batch; do not clear it                              |
| Per-record reject/conflict    | Quarantine only affected records; continue independent valid records                             |
| Missing ACK result            | Treat that record as unacknowledged and safely retry                                             |
| Unsupported schema/server     | Block affected uploads visibly; continue safe local counting if possible                         |

Do not promise delivery while the relevant browser is closed or the extension is removed. `Waiting to sync` differs from `Recorded by company server`. A received-but-pending estimate differs from fully calculated resources. Scheduling/restart tests run against each browser's actual background host; longer-lived Firefox behavior, if available, does not remove the need for durable checkpoints.

### 6.2 Time and counters

- Save `occurred_at` and `received_at` separately. User requests are counted at dispatch occurrence time; a generation's token/resource contribution is assigned to that attempt's start time. Expose this definition for midnight-spanning streams.
- Period boundaries use the configured company IANA timezone. Weeks start Monday; months are calendar months; all ranges are half-open `[start, end)`. Store instants in UTC and convert boundaries using timezone rules, not fixed UTC offsets.
- Changing company timezone requires a re-bucketing job and visible rebuilding status. Do not silently reinterpret historical cached totals.
- Reject/quarantine times more than 5 minutes in the future relative to server time with `clock_skew`. Old offline records within a valid capture era of their original installation remain eligible only if not erased or expired; a same-installation credential renewal does not reset that history or authorize another device's revisions. Never rewrite occurrence to upload time. Live records from before the first valid organization era or from a disconnected/local-only era cannot be uploaded as live observations. Separately observed numeric history follows section 14: its original source date may predate enrollment, while authenticated ownership is established at acquisition. Connecting does not backfill a preexisting personal ledger.
- Summaries include user requests, observed attempts, outcomes and search counts separately. A sync upload is never an AI request.
- Active users/devices are distinct IDs over the entire selected range. Never sum daily distinct counts. Registered users are current memberships and are not a verified human headcount or historical active count.

### 6.3 Summary response

Every summary includes `snapshot_id`, `generated_at`, `range_start`, `range_end`, `timezone`, `time_basis`, `calculation_view`, `aggregate_status`, request/attempt/outcome counts, token/resource series, method groups and coverage metadata.

Every series includes its quantity/unit/scope, contributing request/attempt count, applicable count, unknown count, partial count, unvalidated count and unavailable reasons. Zero applicable records is not 100% measurement coverage. Mixed evidence is never summarized with a single “exact” badge. “No recorded requests” is a distinct state from “requests recorded but resources unavailable.”

Online My usage uses a server snapshot across paired devices; pending current-profile counts and provisional estimates are shown separately. Do not add local all-time totals to the server snapshot. On loss of connectivity, show current-profile local totals and a separately dated cached server snapshot. Conversation bars use the same rule when fetching paired-device conversation totals.

Run nightly canonical-to-rollup reconciliation and a targeted check after migration, deletion or method recalculation. A mismatch marks affected aggregate buckets `inconsistent`, alerts the operator and starts a canonical rebuild. APIs may serve a dated prior valid snapshot or a clearly labeled rebuilding response, never current-looking incorrect totals. Rebuild does not alter underlying observations. Verify rebuild result before returning status to `current`.

### 6.4 Member company privacy

**Owner decision, 13 October 2026 (supersedes the small-group rule).** While `company_sharing` is on (stored value `threshold`, kept for compatibility), members see organization totals and their day, tool and model splits whatever the group size: there is no minimum number of people and no complementary suppression. A period without usage is a current summary of zeros. Members are told that in a small team the totals can reveal one person's usage. `disabled` still hides organization totals from members, and admin views, retention and the other privacy rules are unchanged (admin views changed later, on 18 October 2026: see section 8). The text below records the earlier design.

Member company endpoints expose only approved aggregate dimensions: date period and site, plus model only where the privacy threshold remains satisfied. User/device/IP filters are rejected. Use calendar-day-or-coarser data, threshold five active pseudonyms per reported cell and consistent complementary suppression. Suppress an overall total when its release would reveal a suppressed cell by subtraction; do not return a hidden exact total in JSON or an export.

Allow date-aligned custom ranges, but the suppression engine must evaluate constituent cells and overlapping published totals. This is a disclosure-reduction measure, not a guarantee of anonymity against all auxiliary information or temporal differencing. For a company unable to accept that residual risk, admin policy disables member-company detailed breakdowns or the entire aggregate payload with a clear policy message. Admin views remain available. Do not claim differential privacy without an implemented and reviewed privacy-budget mechanism.

## 8. Administrator views and network observations

**Owner decisions of 17 and 18 October 2026.** By default organization administrators see organization figures only and no connection address is collected. Two operator-level server settings, `person_analytics_enabled` and `ip_collection_enabled`, bring back the earlier per-person views and the address collection without rewriting code. Both default to `false`, live only in the deployment settings file and cannot be changed by an organization administrator. `/v1/config` reports them read-only as `features: {"person_analytics": bool, "ip_collection": bool}`, outside the policy, so switching them never changes an organization's policy version; the admin website shows the per-person pages only when the server says they are on. The public website, privacy texts, legal documents and the extension's texts describe the default (both off).

### Default: both switches off

- Organization administrators see organization totals and aggregate figures only. They never see usage next to a name, email, member id or browser, and never a request list per person. The server enforces this, not only the interface: `GET /v1/admin/summary`, `GET /v1/admin/breakdown`, `GET /v1/admin/people`, `GET /v1/admin/health` and `GET /v1/admin/activity` refuse a `user_id` (or `device_id`) filter with `person_analytics_disabled` 400, and exports and admin recalculations refuse a person or the per-record report with the same answer.
- Small groups are not hidden. Aggregates are shown for any number of people, even one, so in a very small organization (for example one or two people) they can reveal one person's usage. The privacy texts state this plainly.
- People page (`GET /v1/admin/people`): how many people used AI in the period, members, administrators, capacity, the median requests per person, the average requests per person among people who used AI, the most active person's request count without a name, and the number of people per request band. The member list serves access management only: work email, role, number of browsers and status, with no usage per member.
- Member page: role, browsers with their connected-since date and status (no last-seen or last-used times), suspend/reactivate, remove, sign a browser out and delete this member's records (erasure request). A deletion preview or job for one person says what will be deleted and shows no counts and no date range of that person's records.
- Activity page (`GET /v1/admin/activity`): organization requests per day for a period and a table by tool and model with requests, the number of distinct people (a count only) and electricity, carbon and water. No person or email. It never takes a person, in either setting.
- Health page: counts only (browsers connected, browsers synced in the last day, browsers not synced for 3 or more days, and browsers per problem kind and site). No per-browser or per-person list.
- Exports: the organization summary report only; a per-person export made while person analytics was on can no longer be downloaded. Recalculations are organization-wide only, and their status lists only organization-wide jobs.
- Unchanged: member list, roles, suspend/reactivate, browser removal, audit log, organization deletion, policy and plan.
- Not available (404 `not_found`): `GET /v1/admin/requests`, `GET /v1/admin/users/{user_id}/requests/{request_id}`, `GET /v1/admin/network` and `POST /v1/admin/network/access`.
- No connection address is collected: no `network_observations` row is written on upload, no IP key or `ip_retention_days` is required (present ones are accepted and ignored, so a production settings file written for an earlier release still starts), the IP key registry is not initialised and `python -m aift.ip_rotation` refuses to run (`ip_collection_disabled`). `/v1/config` sends `ip_retention_days: 0` so that extensions released before 18 October 2026, which require an integer, keep working.
- Rows stored while IP collection was on stay in the table, shown to no one, until an explicit one-off maintenance command deletes them; nothing deletes them automatically while collection is off. `python -m aift.maintenance purge-network-observations` only counts the rows; with `--confirm` it deletes every row in pages and the empty table stays. The operator runs the deleting form once, after the owner confirms it. Deleting a person still deletes that person's stored rows.

### `person_analytics_enabled: true`

The per-person administrator views as they were before 18 October 2026 come back: `user_id` on `GET /v1/admin/summary` (with its splits) and `GET /v1/admin/breakdown`; `requests` (requests per member id) on `GET /v1/admin/people`; the request list `GET /v1/admin/requests` and request details `GET /v1/admin/users/{user_id}/requests/{request_id}`; the Health list of each connected browser with its member, last upload and latest report; `last_seen_at` on a member's browsers; the per-record export report and the person filter on exports; recalculation of one person; and counts in a person's deletion preview and job. The aggregate People figures and the Activity page stay as in the default.

Usage recorded while person analytics was off is never shown by person afterwards, unless the operator decides otherwise. The server stores the moment it first sees the switch on (`person_analytics_enabled_since`, in the `maintenance_cursor` row `person-analytics-switch`) and every per-person view shows only usage from the first full day after that moment in the organization's time zone (daily totals cannot be split within a day, so the day of the switch is left out entirely). This floor applies to one person's summary and its splits, the breakdown, the People `requests` map, the request list and details, record exports and person-filtered summary exports, the Health list's upload and report times and `last_seen_at`; summaries carry it as `person_analytics_since`. A person's deletion preview shows counts only when none of the records it counts (live or saved) is older than the floor. An administrator reads a recalculation job for one person only if an administrator started it after the switch, and never sees its count of processed estimates, which covers older records too; request details and the request list leave out a shared attempt from before the floor. Switching the setting off records that, and switching it on again starts a new period from the new moment; per-person export files made in an earlier period stay withdrawn.

### `ip_collection_enabled: true`

The previous address collection comes back: each accepted upload writes a `network_observations` row with the connection address encrypted under the active IP key and an equality token; `ip_key` or `ip_keys`, `active_ip_key_version`, `ip_restore_required_until` and `ip_retention_days` are required and validated again (a production settings file without them no longer starts), the IP key registry is initialised at start, the worker deletes rows older than `ip_retention_days` and advances key rotation, `python -m aift.ip_rotation` works as documented in `apps/server/IP-KEY-ROTATION.md`, and `/v1/config` sends the configured `ip_retention_days`. The Network page (`POST /v1/admin/network/access` with a fresh email code, then `GET /v1/admin/network` for 15 minutes) lists addresses next to members and browsers, so it needs both switches on.

### Before switching either setting on

Turning person analytics or IP collection on changes what administrators can see about each member. Before an operator does so, the privacy texts (privacy notice, data processing agreement and website) must be updated to describe it, the extension's connect dialog needs a new member consent text that says so, and in Germany a works agreement (Betriebsvereinbarung) with the works council is needed. ## 9. Policy, deletion and backup contract

Policy fields include company timezone, `pause_mode` (`user_controlled` or `disabled_by_company`), supported sites, usage retention/entitlement version, member-company disclosure, accepted schema/method versions and disclosure version. Self-hosted usage defaults to **until admin deletion**; hosted free live usage also defaults to **until admin deletion** (owner decision of 11 October 2026); an administrator's shorter choice (24, 12, 6 or 3 months) or a configured plan maximum applies as a rolling calendar-month window. The owner-approved numeric-history family is retained beyond this age window as specified in section 14, while explicit erasure remains authoritative. The product specification defines cutoffs, request-family expiry, local queues, derived totals, policy transitions and anti-resurrection on restore. No raw employee prompt/answer content exists on the server to retain. Domain/seat choices still marked pending are not production defaults.

The enrollment disclosure says all supported use in that enrolled Chrome, Edge or Firefox profile is tracked, including personal activity in that profile. Disabled pausing removes the extension pause action and shows the policy; it does not prevent uninstall, browser permission changes or use of another profile. Report lost visibility honestly. If company configuration is unreachable, enforce the last valid acknowledged policy, show its age and never silently switch company origin or widen permissions.

Deletion protocol:

1. An organization admin selects one user ID, a request-dispatch-time range, or explicit company-wide scope. A range selects requests by `dispatched_at` and erases their whole request families, including child attempts that cross midnight; the preview explicitly shows any contribution dates beyond that range. Freeze the range/cutoff in the preview so an all-history deletion does not accidentally prohibit future new usage. Whole-user deletion, in contrast, revokes that identity permanently; the person may later join again only as a new membership (owner decision of 22 October 2026). Preview affected records, aggregates, local-sync consequences, stored connection address rows and exports; a preview that names one person lists what will be deleted without counts or that person's date range, unless person analytics is on and nothing it counts predates the switch (section 8). Require recent reauthentication and an exact confirmation tied to that preview.
2. Create an idempotent job with states `pending`, `applying`, `rebuilding`, `completed`, `failed`. Immediately record the deletion marker/epoch before erasing canonical records, so an offline device cannot race resurrection.
3. An erasure is a clean slate when it is made (owner decision of 22 October 2026). Uploads built before the browser applied it are refused (`deletion_sync_required`, `deletion_epoch_changed`) and none is taken while it is applied (`deletion_in_progress`). For a deleted time range, reject future live uploads for that user/range with `erased`, regardless of newly invented local UUIDs. A record ID tombstone also handles already known records with altered timestamps. A saved message read again after the erasure counts again, in the browser and in the organization totals: the server stores its reading time against the server clock (just after each erasure that covers it, never later than the server clock otherwise) and answers `erased` only for an erasure whose time it does not know; the browser keeps out only messages it read before it applied the erasure, and messages the server refused. A restore that replays an erasure removes only messages read before it. For a deleted user, revoke all devices, reconnect proofs, sessions, bootstraps, pending connections and login continuations and prevent that identity from being recreated by retries. Remove email mappings according to the authorized identity-deletion scope; a deliberate future fresh membership cannot reclaim erased records or keys.
4. Remove canonical observations, revisions, estimates and affected stored connection address rows; invalidate exports/caches; rebuild affected aggregates. Mark in-progress summaries as rebuilding. Preserve only minimal deletion markers and audit evidence necessary to enforce erasure, not the erased measurements.
5. Devices fetch deletion changes before draining an old queue and on ordinary sync. On a revoked/deleted response, check the separate deletion-receipt channel before offering reconnection or retaining a queue indefinitely. Verify the signed company/device-scoped instruction, durably purge affected local metadata/cached summaries, then acknowledge the epoch. For full-user deletion, also remove usage credentials and key material. A company-wide erasure applies the range its preview froze and keeps the device's credentials, because members and devices stay active; only full-user deletion ends the connection. Retain only the pending receipt capability until acknowledgement completes. The server keeps the minimal credential hash/tombstone needed to deliver erasure, independently of deleted membership data; it provides no usage access. A normally revoked but non-deleted device receives no purge command and retains its queue as specified. Offline devices cannot be physically wiped remotely while disconnected; the server prevents reingestion and the admin UI states device acknowledgement coverage.
6. `completed` requires active-database/aggregate/export work verified and connected-device acknowledgement tracked separately. Do not pretend disconnected devices or already-downloaded third-party exports have been erased. State those limitations in the completion report.
7. Proposed backup retention is 30 days, distinct from primary usage retention; disclose it. Keep a protected deletion/expiry journal outside the normal rollback window and replay applicable deletion markers and retention cutoffs after restoring a backup, before serving data or accepting uploads. A later longer retention plan cannot restore previously expired records. Test backups taken before deletion/expiry. If the journal is missing, restore stays unavailable pending operator resolution.

Backup encryption and authenticated application encryption solve different problems. Document key backup/recovery separately and test it. No target VPS or real server hostname/IP is selected or written into this plan.

## 10. Health, logs and release compatibility

Health records contain category, code, severity, affected site, first/last timestamps, affected record counts, last successful operation, next retry and a safe action. They never contain prompt snippets, file paths, raw URLs, headers, tokens or unsanitized stack messages. Send health at browser startup and at most every 15 minutes while the relevant browser's activity/lifecycle permits; this is reporting health, not evidence of AI use.

Badge priorities: storage/capture failure > revoked/auth-blocked > synchronization blocked > partially measured/pending > normal recorded state. Details expose all concurrent issues; priority does not erase a lesser issue. A badge can be shown when durable logging is broken. An inactive installation is **not reporting**, not “not using AI.”

Data-only method/config updates require signature/hash/version checks. On invalid update, retain the last valid supported bundle with an explicit stale/update-failed indicator; when it is inapplicable or no bundle exists, resources are unavailable. Extension code/adapter updates use normal published extension updates. Database migrations are transactional where possible and have preflight backups, tested upgrade paths and a compatibility matrix. Never roll back a binary against an incompatible schema; keep the service in maintenance mode with a recovery instruction.

Before implementation claims completion, generate and run the test IDs in the acceptance matrix. A plan without the promised schemas, fixtures and failure behaviors implemented is not a verified product.

## 11. Schema 1.2.0 amendment: extracted document text (10 September 2026)

This amendment adds numerical, request-scoped extracted-file text coverage. It does not change the estimator, give local extraction evidence of provider processing, or authorize associating an uncorrelated worker result with a request.

### Version compatibility and immutable history

Observation schema `1.1.0` remains a strict, frozen whitelist. Its archived JSON schemas, original payloads, canonical JSON hashing, revision receipts and original estimates remain unchanged. Do not add a default field, rewrite an old record, or rehash historical observations when projecting a newer display. The `1.1.0` batch envelope continues to contain only `1.1.0` records. A `1.2.0` batch may contain exact `1.1.0` and `1.2.0` records together; each record is validated by its declared version. Unsupported versions fail closed. Identifiable invalid records receive safe per-record rejection without preventing independent valid records in the batch from progressing.

The `1.2.0` attempt shape is unchanged apart from its declared version. A `1.2.0` request additionally requires `documents.extracted_text`, with no implicit default. It is either `null` or a list of these strict components:

| Field                   | Contract                                                                                                                                                                                                                                             |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `component_id`          | Lowercase random UUIDv4, unique within this request. Never derived from file content, filename, URL or a reusable upload identity.                                                                                                                   |
| `origin`                | `new_upload`, `retained_context`, or `unknown_origin`, based on verified request association.                                                                                                                                                        |
| `extraction_profile_id` | Approved immutable profile `local-file-text-utf8-pdfjs6.3.289-opc-v1` or `observed-inline-file-text-v1`. Profile identity describes how text was obtained, not a provider tokenizer.                                                                 |
| `page_count`            | Observed integer 0 through 200, or `null`; unknown pages are not zero.                                                                                                                                                                               |
| `tokens`                | Strict extracted-file text measurement specified below.                                                                                                                                                                                              |
| `missing`               | One through eight distinct codes from `provider_processing`, `ocr`, `image_encoding`, `retrieval_selection`, `layout_and_drawing_text`, `rendered_visibility`, `formula_recalculation`, `external_font_mapping`. Must include `provider_processing`. |

The `tokens` object has the same numerical `value`, `profile_id`, `reason`, and completeness fields as other token measurements, but `scope` is exactly `extracted_file_text`. A known value is a decimal Counter string within the existing signed BIGINT bound, including a legitimate observed zero. It requires `evidence: heuristic_estimate`, an approved tokenizer profile, a non-null approved reason, and completeness `complete_for_scope` or `partial`. An unknown value is `null` with `evidence: unknown`, completeness `unknown`, and an approved reason. There is no implied provider-reported, officially mapped or calibrated count. Ordinary token fields do not accept this scope.

Components share the existing per-request bound: extracted-file components plus input-image groups plus requested image operations total at most 100. If `documents.upload_count` is known, it cannot be smaller than the number of `new_upload` file components. Retained components do not increment upload count. Upload counts/types/provider-processing classifications are independent observations; successful local extraction must not silently alter them.

`null`, including the read projection of an absent historical `1.1.0` field, means unknown or unassociated extraction coverage. An empty list means an observed empty set of correlated extracted-text components. Neither means provider processing is zero. The private file worker returns unassociated results with `telemetryAllowed: false`; only a separately verified provider correlation may produce a component. No filename, document text, URL, provider file identifier, content hash, storage key or file byte sequence enters telemetry.

**Observed inline file text profile (10 September 2026).** The approved prerelease 1.2 whitelist additionally accepts immutable `observed-inline-file-text-v1`. This profile counts the exact accessible Claude completion-dispatch `attachments[].extracted_content` strings for the reviewed `text/plain`, `kind: file`, `origin: user_upload` shape. It does not run local PDF/Office extraction or establish full original-document fidelity. Preserve strings without joining separate attachments or normalizing their content. Count in the bundled worker with unverified tokenizer mapping, `page_count: null`, and missing `provider_processing`, `ocr`, `image_encoding` and `retrieval_selection`. Completeness applies only to the observed inline string. Unsupported shapes, formats, over-limit sets and inaccessible text retain unknown extraction coverage; a failed count is unknown, never zero.

The producer admits at most 16 inline components and 262144 UTF-16 code units across their strings, within the existing combined capture and worker memory limits. Raw strings stay transient. Only random request-scoped position IDs and numerical components survive restart; revisions replace the component set. `user_upload` describes provenance and does not prove a new upload for this dispatch, so this producer uses `unknown_origin`, null upload count and unknown provider processing without stronger independent evidence. An empty current inline set proves no retained-file absence and triggers no retained-file recount. This whitelist addition rewrites no historical 1.1 or existing 1.2 observation or payload hash.

### Identity, correction and lifecycle

Correlate at most one component for the same actual extracted input within one request. Re-observation and corrections retain that request's component identity; repeated observations are revisions, not additions. A genuinely retained input in another request may receive a fresh request-scoped identity and `retained_context` origin. Random component IDs cannot establish equality across installations. Verified request alias reconciliation keeps the canonical request's one component set; it never unions random component IDs from duplicate observations. Unverified identity cannot justify merging requests.

A revision replaces the old request contribution transactionally. Deletion, retention, replay of the protected erasure journal and anti-resurrection apply to the complete request family, including the file metadata and all derived projections/exports. Server migration `0005` marks existing populated aggregates rebuilding and invalidates old exports, then the bounded worker rebuilds projections. It does not rewrite observations, original estimates, historical revisions or receipt hashes.

### Summaries, exports and disclosure

Extracted text is **non-additive** to all ordinary token fields and all energy/carbon/water quantities. It has no energy coefficient in this amendment. Summary `file_text` entries remain grouped by origin, extraction profile, tokenizer evidence and tokenizer profile. Each entry includes `quantity: extracted_file_text`, `unit: tokens`, `scope: extracted_file_text`, `additive: false`, an exact fixed-point integral `value` or `null`, `applicable_count`, `contributing_component_count`, `unknown_count`, `partial_count`, `unvalidated_count`, `reason_counts` and `missing_counts`. Aggregated values may exceed the individual Counter bound and follow the existing exact aggregate decimal limit. These are component denominators, not attempts or uploaded files. Do not sum incompatible profiles or imply a cross-profile total.

`file_text_coverage` separately provides decimal-string `observed_request_count` and `unknown_request_count`, with the same scope and `additive: false`. An unknown historical field is not silently treated as an observed empty array. Summary CSV adds separate component-series rows and `file_text_observed_request_count` / `file_text_unknown_request_count` rows using request-dispatch time, complete measurement grouping and missing/reason counts. Request detail and record exports preserve the exact original versioned metadata.

(Superseded on 13 October 2026; see 6.4.) Ordinary member-company summaries apply the existing threshold and complementary suppression to each constituent day/site, file coverage population, origin/profile group, known/unknown/partial/unvalidated component count, and missing/reason category or arithmetic complement. Suppress the whole result if any disclosed constituent is too small. Both original and recalculated views obey this rule; authorized admin views retain complete scoped counts. The UI must visibly separate extracted text, its unknown/partial coverage and provider processing, and must not present it as additional inference consumption.

**Request-population complementary suppression (migration 0006; superseded on 13 October 2026, see 6.4).** Component-group thresholds alone are insufficient: six disclosed request contributors, five with observed components and one with an empty set, would expose the sixth person's absence. The server must additionally protect request-level component presence and its absence complement, and the presence/absence of every disclosed file measurement group, within each constituent day/site. At least five people must contribute to each nonempty disclosed complement. This applies even when every positive component group separately has five contributors, and to both original and recalculated summaries. Private derived request-presence metadata supports these checks; it is not an additional public quantity. Older derived data stays unavailable until rebuilt. Migration `0006` makes this projection change explicit while preserving all original observation/revision/receipt/estimate bytes.

## 12. Recorded-thread relation amendment (10 September 2026)

This separate API amendment links an observed Perplexity thread route to already-recorded owned requests. It does not change observation schema 1.1.0 or 1.2.0, canonical observation bytes, original payload hashes, originating-device revision ownership, provisional `conversation_key` values, estimator inputs or global usage totals. A relation is observational metadata, not proof of provider execution or tamper-proof attestation.

### Evidence and derivation

The reviewed passive relation is the existing host-initiated `/rest/thread/<UUID>` response for the matching `/search/<UUID>` route. An accepted entry has the same `thread_url_slug` and an observed `frontend_uuid` identifying a dispatch. Neither context UUID is a substitute. Do not infer active-send membership from the current URL, import history as new usage, count its text or media, issue private provider requests, or automatically fetch more pages.

Live follow-ups (5 October 2026, owner decision): a send from the page of thread T that names a previous answer P (`last_backend_uuid`) continues the thread that holds P. When it is sent, the extension links the send to T only when P is proven part of T, so the bar counts the reply live: P equals T, because Perplexity gives a thread the id of its first answer; or P is a reply saved from T's reviewed thread response; or P is a live reply that answers a request already linked to T. A send from outside a thread (the home page or Perplexity's provisional `/search/new/` address) starts a new thread, which opens at the id of its first answer while that answer streams. When the same page then opens `/search/T`, the extension links the send to T only when the reply's own id (`backend_uuid`) equals T, so its bar also counts live; a page in another tab or document proves nothing. The route only names the candidate thread and never proves membership. The page's address is the one the browser last reported for the tab, because the sender address of a message keeps the address the page loaded at after in-page navigation (seen 5 October 2026); a restarted background reads the open Perplexity tabs' current addresses before it handles any message. A reply already saved in or linked to T joins T again by its own id, as after a worker restart forgot the link of a capture still running. The link uses the same relation write below, so the server sees one more already-recorded request of the thread.

Inside a trusted extension context, derive `thread_key` with the existing length-prefixed HMAC tuple, site `perplexity`, key version `1`, and identifier kind **`route`** over the route UUID. Derive `provider_request_key` with the existing identifier kind **`request`** over the observed frontend UUID. A route key is separate from a wire conversation key, even when source identifiers happen to match. Raw provider IDs, URLs, titles, page bodies, prompt/answer text and binding nonces are absent from server payloads and logs.

### Strict relation write

`POST /v1/me/thread-relations` requires an authenticated active installation at the server origin where it enrolled. Its exact JSON fields are:

| Field                   | Required value                                      |
| ----------------------- | --------------------------------------------------- |
| `site`                  | `perplexity`                                        |
| `key_version`           | `1`                                                 |
| `thread_key`            | Lowercase hexadecimal HMAC-SHA256, 64 characters    |
| `provider_request_keys` | One through 100 unique lowercase 64-character HMACs |
| `deletion_epoch`        | Current tenant epoch, nonnegative safe integer      |
| `source`                | `perplexity-thread-response-v1`                     |

Unknown fields, duplicate candidates, raw IDs, page metadata and unsupported versions are rejected. Authentication supplies tenant, owner and installation identity; callers cannot override them. Writes serialize with tenant ingestion and deletion. Stale epochs reject with `deletion_epoch_changed`; pending deletion or aggregate rebuilding is unavailable for retry. A conflicting existing membership rejects the entire batch with `thread_relation_conflict`, without partial mutation.

Resolve only retained canonical Perplexity requests owned by the authenticated member. A paired installation can associate its member's already-recorded canonical request without revising it. The natural key is `(tenant, owner, provider_request_key)`: repeating the same thread membership is idempotent. The ordered response is `{site, key_version, thread_key, deletion_epoch, results}`, where each result contains only `provider_request_key` and `status: linked | not_recorded`.

Unmatched keys are query inputs only. They create no durable relation, pending job, receipt, observation, usage counter, IP observation or diagnostic body. A client may retry after ordinary ingestion, but the server does not materialize a relation automatically when that request later arrives. Not-recorded does not distinguish another user's key from an absent key. Partial response-page coverage remains explicit in the client; it cannot turn unmatched entries into zero usage or a complete thread claim.

### Matched recorded subset

`GET /v1/me/recorded-threads/{thread_key}/summary?period=all` requires the same active-installation authorization. An omitted query also means `period=all`; other filters are rejected in this amendment. The response is:

```text
{
  status: matched_recorded_subset | unavailable,
  site: perplexity,
  key_version: 1,
  thread_key: <opaque route HMAC>,
  deletion_epoch: <current epoch>,
  coverage: {
    scope: matched_recorded_requests,
    provider_history_complete: false,
    matched_request_count: <exact integer string>
  },
  summary: <existing own-user original numerical summary> | null
}
```

The match count and numerical request selection use the same retained, owned, site-specific population within the existing `period=all` summary window. No matches in that window means `unavailable` and `summary: null`, not a successful zero-total conversation; an otherwise retained relation remains available for later windows. If any selected request has unresolved request identity, the entire subset returns retryable HTTP 409 `thread_identity_unresolved`, preserving the relation and original observations rather than silently excluding the ambiguous request. A matched subset is never complete provider history. The server does not assert page completion, number of provider pages, unobserved history size or client pending candidates. Deletion and rebuild guards take precedence over returning current-looking partial database work.

Selection uses canonical request identities and canonical attempt membership, including existing verified request-attempt links. Each canonical contribution appears once even if multiple related requests share it. Existing exact counters, compatible method/evidence grouping, non-additive file quantities, original estimate views and request-family retention apply. This endpoint exposes only the authenticated member's records and provides no company-group subtraction filter.

### Cleanup, restore and compatibility

`recorded_thread_relations` has a scoped foreign key to the canonical request's unique `(tenant, owner, kind, stable_key)` identity, with `kind=request`, and an indexed `(tenant, owner, thread_key)` lookup. Canonical family deletion cascades to the relation; retention filtering excludes expired parents before physical cleanup. Unknown keys have no durable state to resurrect. A stale deletion epoch cannot reintroduce a mapping, and a refreshed retry still requires a surviving retained owned request.

Migration `0007` adds this table and advances the schema/readiness guard to 7 without rewriting prior observations or aggregates. Offline restore verification requires the current schema, replays the protected erasure journal, drains cleanup/rebuild work and verifies relation referential scope. A restored old relation cannot survive erasure of its canonical parent. The client must likewise clear related local metadata and cached displays at the committed erasure boundary, without deleting independent user settings.

## 13. Authenticated extension method delivery (14 September 2026)

This implements Sections 4.2 and 10 without changing observation schemas, original estimates or default capture methods. Personal mode uses the packaged baseline configuration and never contacts a product server for method updates. Installing a signed alternative does not activate it. Recalculation requires an explicit selected method; an unknown, corrupt or unavailable requested method is an error, never a silent baseline substitution.

### Enrollment trust and delivery

Deployment settings may provide `method_public_key`, a base64 DER P-256 SubjectPublicKeyInfo public key independent of the deletion key. Only the authenticated `/v1/connections/exchange` response provides this key to the extension. The client pins it to the exact company origin, organization/member namespace, installation and enrollment era. Public config, policy refresh and update envelopes cannot replace it. Changing the key requires authenticated re-enrollment. Legacy enrollments without this field remain usable with packaged methods and explicit `trust_unconfigured` update diagnostics.

An active authenticated installation may make these GET requests at its paired origin only:

| Path                                | Exact response                                                                                                                                                             |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/v1/me/method-updates`             | `{delivery_status: available or trust_unconfigured, trust_fingerprint: SHA256 of enrolled SPKI bytes or null, methods: [{method_id, method_hash, issued_at, expires_at}]}` |
| `/v1/me/method-updates/{method_id}` | `{bundle, bundle_hash, issued_at, expires_at, signature}`                                                                                                                  |

The index has at most 31 alternatives and a 64 KiB client limit. Each envelope has a 2 MiB UTF-8 limit. Identifiers are at most 128 lowercase letters, digits, dots and hyphens and must begin with a letter or digit. Query parameters, arbitrary URLs and write operations are rejected. The client rejects redirects and mismatches between the index, complete envelope, enrolled key fingerprint and immutable bundle identity. No verification key, code, expression evaluator or dynamic module is accepted from the envelope. The production update verifier rejects `test-linear-v1` and non-HTTPS or credential-bearing source links.

The complete envelope is copied and frozen before any asynchronous verification. Its signature authorizes the canonical JSON header containing exactly `bundle_hash`, `issued_at` and `expires_at`; that hash must match the same snapshotted bundle. Signatures use ECDSA P-256/SHA-256 and base64 IEEE P1363 `r || s`. Runtime delivery timestamps use UTC ISO milliseconds. New admission requires an unexpired approval and allows at most five minutes of future issue-time skew.

### Durable admission and historical validity

IndexedDB version 9 adds `method_catalogs`. Admission is one transaction after all requested envelopes validate. It compares the original connection identity, enrollment ownership interval, erasure generation and prior catalog hash again before writing. The catalog contains at most 31 alternatives, bounded to 8 MiB including receipts. Each connection catalog retains its first accepted envelope and, when renewed, its latest delivery approval. A local installation-key MAC binds these records, admission times and connection provenance; restart verifies this integrity and each original signature before exposing a method. This is protection against corrupt or substituted cache records, not a claim against an attacker controlling all privileged extension storage and keys.

Expiry gates new admission. A previously accepted immutable method remains available for a new explicit recalculation after its delivery envelope expires, with a stale-freshness disclosure. There is no caller-controlled historical flag or admission timestamp in a runtime/API request. Re-enrollment with different trust creates a separate active catalog context; another company or installation cannot populate the current context. Full namespace erasure removes its catalog. Range/retention erasure invalidates in-flight work and numerical cache results; non-personal scientific bundle metadata need not be erased with an individual request.

Server renewal uses one purpose-tagged `method_delivery_v1` record per approved method in the existing `maintenance_cursors` table. It does not modify `method_bundles`, their original approvals, observation history or historical estimates. The local `--renew-delivery` command requires the same already-approved bundle hash, a valid signature under the independently configured key and a later issue time. It can replace only current delivery approval metadata. No new server schema migration or HTTP installation/renewal route is introduced.

### Selection, failures and bounds

The extension uses a scoped explicit estimator bundle resolver; authenticated downloads never register methods in the legacy process-global test registry. Local recalculation scans retained canonical observations in existing bounded pages, preserves original method hashes and produces separate `recalculated` results without rewriting observations, outbox rows or original estimates. Summary cache identity includes selected view, immutable method hash, connection trust and existing numerical/erasure versions. Selection does not change future captures, personal ownership or enrollment history.

The UI-facing `calculationView`/`methodId` selection becomes `calculation_view`/`method_id` only at the server query boundary. Successful local and server views return authoritative `calculation: {view, methodId, methodHash}`. Failed or pending requests cannot relabel previously displayed values. Server summaries must match the installed selected hash and preserve existing current-revision readiness and privacy checks. Own-member preparation/status uses the existing recalculation API; preparing an organization-wide view still requires its administrator. Job status alone is not proof of a current numerical summary.

Method-status and numerical UI responses also carry the same opaque `scopeToken`, derived locally from the verified connection trust, ownership generation and erasure generation. The numerical reader revalidates that authority at final return. A UI combining separate status and summary requests must require exact token equality and discard mixed-scope responses, including company-to-company switches. Access-token refresh and ordinary usage progress do not change this authority token. It contains no raw company/user identity, key or credential.

Method diagnostics expose bounded state `baseline_only`, `loading`, `current`, `stale` or `failed`, fixed reason codes, check/last-valid timestamps and trusted bounded display labels/source metadata. Invalid updates retain the last valid supported catalog. Failed storage and timeouts also remain visible in memory when a durable failure write is impossible. Automatic checks occur only during paired company maintenance, no more often than five minutes; explicit checks are coalesced with a one-second minimum retry interval. There is one physical update operation, one envelope download at a time, a 30-second logical operation deadline and 20-second request deadlines. Unsettled canceled work continues to occupy its physical slot. Scope, permission and erasure changes prevent late admission or publication. No source URLs are fetched, and no method operation uploads provider text or previously personal observations.

## 14. Numeric history observed while the user loads a conversation

**Presentation amendment, 14 September 2026:** the owner's [compact presentation decision](../decisions/2026-09-14-historical-conversation-counting.md#compact-presentation-amendment-14-september-2026) permits a provisional combined extension display under Requests. Earlier prompts are included after existing confirmed-match/conflict exclusion. Unverified overlap remains visible as an approximate count and Matching incomplete status, with numeric diagnostics in Details and a Methodology explanation. This display does not mutate or change the separate API projections and their invariants below. Compatible tokenizer profiles and text-resource methods may combine; other groups and local/pending/synced snapshots remain separate. The first-message loading hint is independent of partial estimation.

The owner decision dated 14 September 2026 expands the earlier no-import boundary. This section governs the separate `history_message` family, version `1.0.0`; it does not change the frozen live observation schemas or reinterpret a history response as a dispatch, stream, retry or execution.

A historical message contains a role (`prompt` or `response`), site, scoped opaque conversation/message/parent/prompt identities, optional independently proved live request/attempt identities, numeric token measurement, separately measured inline-file text, and immutable method ID/hash. Raw source text is processed transiently in the private counting worker. Raw provider IDs, message text, titles, file names, URLs, capability tokens and content hashes do not enter the historical ledger, outbox or API. `historyNumericPayloadHash` hashes only the allowed numeric/categorical payload, excluding its import timestamp; it is not a text-content fingerprint. Message HMAC input includes conversation identity and role, so source-ID reuse in another conversation cannot merge unrelated messages. The local row may also keep a count basis (text and file text lengths, counting runtime and the resulting counts) so an unchanged finished message is not counted again. It is local-only, contains no text or content hash, and never enters the outbox or API.

`occurred_at` is the nullable original UTC source date, retaining millisecond or microsecond precision. `date_basis` is `message_created`, `entry_created`, `turn_created` or `unknown`; it is `unknown` exactly when the original date is null. Entry/turn dates are not presented as execution start or completion times. `observed_at` is the separate local acquisition time. Server authority is the authenticated user/installation and its enrollment at acquisition, not membership at the old source date. Unknown source dates remain in an explicit undated bucket and are excluded from dated queries. Timestamp comparisons normalize precision without truncating the stored source value.

Passive provider capture remains bounded to the provider's own user-triggered history traffic. It never privately fetches, paginates, scrolls or sends a prompt. One admitted start/page lifecycle can contain at most 1,000 messages within the provider reader's 1 MiB limit. Counting and persistence advance in chunks of at most 100 under the original document/navigation, ownership and erasure authority, with the existing two-operation/30-second admission boundary. A canceled later chunk cannot undo previously committed valid chunks or claim complete coverage. Stored parent links and selected head resolve branch membership before date/model/site filters. A proved first request remains a coverage fact, not evidence that hidden provider work or every branch has been observed. `provider_history_complete` stays false.

`POST /v1/me/history` accepts exactly `HistoryPageSchema`, at most 100 messages and 256 KiB of numeric JSON, including the optional `company_dedup_keys` list (section 5.2). A page that would exceed the limit leaves its last messages for the next upload. It requires an active authenticated installation and the current deletion epoch. Its ordered receipts contain only `message_key`, `payload_hash` and status `applied`, `duplicate`, `conflict` or `erased`. Repeated imports and paired installations share canonical per-user message identities. Identical numeric payloads are idempotent. Only absence-to-observation refinements are ordered without a provider revision proof; contradictory known dates, identities, token measurements or inline-file measurements create an explicit conflict. The proposed method is the estimation release of the uploading browser, not part of the message: a stored message keeps its first method, as the browser keeps it locally, and a later copy that proposes another method is compared as if it proposed the stored one (15 October 2026; before, a second installation, a reinstall or a newer release made every such message a conflict). A reread that could not count (an unknown token measurement where a known one is saved) contradicts nothing: the saved measurements stay. A server conflict clears when an installation other than the one that stored the message sends a copy these rules accept; the stored installation's own agreeing copy clears nothing, because the server keeps no copy of the read that contradicted it. The receipt is `conflict` whenever the stored message stays a conflict. A conflict the browser found itself is cleared when a later read matches the saved record again; a conflict reported by the server stays until the server accepts a later copy from this browser (receipt `applied` or `duplicate`). Original payloads and original historical assessments remain stored separately. No conflict overwrites a live observation or original estimate.

`GET /v1/me/history/{conversation_key}/summary?period=all` exposes historical totals independently of recorded-live conversation availability. Normal My/Company/admin summaries also carry a separate `history` projection; company projections obey the sharing policy and, since 13 October 2026, apply no contributor or complement suppression whatever the group size (section 6.4); admin projections are organization aggregates only (section 8). The extension keeps local, pending and synced projections distinct. Its method selection does not silently recalculate historical originals.

Summary invariants are explicit. `observed_prompt_count` and `observed_response_count` include every unique retained loaded message, including conflicts and proved live matches. `prompt_count` and `response_count` are imported contributions, excluding conflicts and proved live matches. Observed total equals imported contribution total plus matched-live count plus conflict count. Dated plus undated equals observed total. Calculated plus uncalculated equals imported contribution total. Unresolved overlap is disclosed and is never automatically added to live totals. Matching requires the reviewed provider identity relation, scoped user/site and canonical record; internal historical prompt pairing alone is not a live match. Resource groups preserve their full method/profile/availability identity, remain partial and unvalidated, and use the existing pure output-based equations without inventing execution evidence. Historical inline-file quantities remain separate and non-additive.

Imported history is exempt from live age cleanup, including any shorter retention period an organization chooses. Explicit erasure remains authoritative. Range erasure includes undated imported messages conservatively and previews their separate count. Persistent message/stable-identity tombstones block altered-date and repeated-load resurrection. Migration 0008 distinguishes new live age-cleanup tombstones from explicit erasure; ambiguous legacy tombstones remain conservative. The IndexedDB migration only recognizes the exact prior production company age-marker shape, whose null start distinguished signed age cleanup from explicit ranges. Full erasure and restore replay cover historical rows, assessments, coverage and queues.

Personal observations stay local. Connecting never queues old personal records. Newly observed connected history follows its captured company authority. Clearing Personal data rotates the analytics namespace and keeps no message-level erasure markers or erasure key: a full Personal clear is a clean slate, so a conversation reopened afterwards is imported and estimated again under the new scope. Range and single-message erasures remain scoped to the namespace in which they were made. A full Personal clear also flags any organization namespace marker (`company:<organization>:<person>`) left in the browser; it never removes one by itself. The flagged marker goes only when the server later issues connection credentials for that same namespace, which it does only for an active membership (a deleted person never gets the same user id back). An unflagged marker, a marker whose membership the server refuses or replaces, and every range, request and attempt marker of the namespace stay, and a later erasure of that namespace writes a new, unflagged marker (owner decision of 20 October 2026).

Historical queues and coverage retain their captured installation device as local routing metadata. Reconnecting the same installation to the same company/user can upload records from its prior enrollment eras without rewriting source dates, import dates or original observations. A different tenant, user or device cannot adopt that queue. IndexedDB migration 11 binds legacy entries only when an exact saved enrollment-era/namespace record identifies one device; missing or contradictory bindings remain unsent. A live `retention_expired` receipt purges the live request family without creating historical erasure markers. An explicit `erased` receipt remains authoritative for linked imported history.

`GET /v1/me/history/export` is an authenticated, paged numeric export, with optional `conversation_key` and opaque `cursor`. Each page contains at most 100 observations with source dates/basis, original payloads, numeric payload hashes and pinned original/current historical assessments, plus `next_cursor` and deletion epoch. Exported copies cannot be remotely erased. The standard deletion preview additionally exposes `historical_message_count` and `undated_historical_message_count` without folding them into live execution counts.

The initial historical summary lookup is capped at 10,000 retained messages per requested population and fails visibly as unavailable beyond that cap. This is an explicit implementation bound, not a performance certification or complete-history claim. Browser-native lifecycle/performance, PostgreSQL concurrency and deployment gates remain separate release checks.
