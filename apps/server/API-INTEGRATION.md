# Server integration

All mutations use strict JSON (extra fields rejected), except the tightly bounded registration bootstrap form. All responses are `Cache-Control: no-store`. Exact configured HTTPS origins are required. Every hosted organization is served at the one registration origin; there the organization comes from the request's own credential (Bearer token, `__Host-aift` session, refresh token, connection id, email-code challenge or deletion receipt device id). A self-hosted server resolves its one organization from its host. Clients cannot submit a tenant/user in usage. Every `company_origin` in a response is the public origin: the registration origin when hosted, the self-host origin otherwise. API version is v1, observations 1.1.0, connection protocol 1.0.0.

Web login: `POST /v1/auth/otp/request` with `{purpose:"login",email,dispatch_id:UUID,registration_id:null}`. Response has `challenge_id`, `delivery_state` (`accepted`, `delivery_unknown`, `failed`), `expires_at`, `retry_at`, `error_code`. Accepted means provider accepted, not inbox delivery. `POST /v1/auth/otp/verify` with `{challenge_id,code,verification_id:UUID}` establishes `__Host-aift` Secure/HttpOnly host-only session, and returns `role`, `destination` (always `/admin`), `csrf_token`. Only active administrators sign in on the website; anyone else gets `admin_required` 403 with no session and no new member. At the hosted origin the code is sent whether or not an organization uses the email domain; `organization_not_found` 404 comes only after a correct code. Free email domains get `work_email_required` 400 at once. Failed OTP is a safe error with no identity echo.

Session restore: `GET /v1/auth/session`, credentials include. Returns role, user_id, company_id, company name, CSRF token, expires_at. Web mutations send `X-CSRF-Token` and browser's exact `Origin`; cookies never authorize another tenant. `DELETE /v1/auth/session` logs out. Operator paths are `/v1/operator/auth/otp/request`, `/verify`, `/session`, on separately configured operator origin and separate cookie. Request purpose `operator_login`; allowlist is deployment-only. Developer actions that change an organization's service state (`PUT /v1/operator/organizations/{id}/status`), assign a plan (`PUT .../entitlement`), grant, revoke or replace an exception (`POST .../exceptions`, `DELETE .../exceptions/{exception_id}`, `POST .../exceptions/{exception_id}/replace`), cancel or review a plan transition, approve a domain (`POST /v1/operator/domain-claims`) or delete a contact request (`DELETE /v1/operator/contacts/{id}` with `{idempotency_key, reauth_token}`) need a `reauth_token`: request purpose `operator_reauth` at `/v1/operator/auth/otp/request` with the signed-in developer's address (the code goes to the configured address), verify it at `/v1/operator/auth/otp/verify`, and use the single-use token within 5 minutes. A missing token is 422, a wrong, used or expired one (or an organization administrator's token) `reauthentication_required` 403. The code is checked after the not-found and stale-version checks, and a retry with the same idempotency_key replays its answer without a new token. Reads, plan version creation and contact request status changes need no code.

Registration `POST /v1/organizations/registrations`: company_name, website (HTTPS), country (two uppercase letters), work_domain, admin_email, registrant_name, registrant_role, terms_version/disclosure_version (`1.0.0`), authority_acknowledged true, idempotency_key UUID. There is no address field: one hosted organization per work email domain unless the developer approved a domain exception. OTP request purpose registration plus registration_id. Hosted verification signs the administrator in at the registration origin (`__Host-aift` plus the registration cookie, one shared `csrf_token`) and returns `destination` `/admin`; self-hosted verification returns the bootstrap hand-over destination on the self-host origin. Only active verified routing reaches tenant admin.

Connection code: `POST /v1/connections/otp/request` with `{email,dispatch_id:UUID}` from the extension returns the challenge result with purpose `connect`; the organization is found by email domain at the hosted origin or by host when self-hosted. `POST /v1/auth/otp/resend` also accepts a connection challenge from the extension. Connection creation: `POST /v1/connections` with verifier_challenge (lower SHA256 hex), challenge_method `S256`, browser_family (`chrome`/`edge`/`firefox`), protocol_version `1.0.0`, operation_id UUID, challenge_id UUID, code (6 digits); optional resume_device_id and installation_reconnect_secret must occur together. The code allows 5 attempts, expires and is single use; the member is created as a `user` if missing (`capacity_reached` 409, `member_unavailable` 403 for a removed member, `organization_not_found` 404). A resume device unknown in this organization is ignored; a wrong secret or owner is `connection_denied`. Returns connection_id, state `verified`, expires_at (10 minutes), company_name, company_origin, policy, deletion_public_key, poll_interval_seconds 5. `POST /v1/connections/status` and `/cancel` take connection_id and verifier (32-128 URL-safe characters). `/exchange` takes connection_id, verifier, exchange_id UUID, policy_version (the organization's current one, else `policy_changed` 409) and disclosure_acknowledged true.

Successful exchange returns company_id, company_name, user_id, device_id, access_token, refresh_token, access_expires_at, refresh_expires_at, installation_reconnect_secret, deletion_receipt_credential, key_version, user_hmac_key, policy, enrollment_era `{id,device,start,end,policy_version}`. Persist before clearing exchange state. Same proof/exchange ID retries return original credentials for 24 hours unless revoked; expiry does not restart. `POST /v1/auth/refresh` takes refresh_token and operation_id UUID. Same old token/operation repeats cached rotation for two minutes; different-operation reuse revokes the family.

Extension endpoints use `Authorization: Bearer access_token`: `/v1/config`, `/v1/usage/batches`, `/v1/me/summary`, `/v1/me/conversations/{key}/summary`, `/v1/company/summary`, `/v1/deletions/changes`. `POST /v1/connections/disconnect` with `{operation_id:UUID}` stops only current installation, closes its capture era, and revokes its token families. The same operation and old access proof return the original disconnect receipt for 24 hours after revocation. Security revocation of a different installation uses `DELETE /v1/me/devices/{id}`, a web session and `{reauth_token,reason:"security"}`.

Policy: policy_version, disclosure_version, timezone, pause_mode (`user_controlled`/`disabled_by_company`), company_sharing (`disabled`/`threshold`), usage_retention_months (null means until admin deletion), ip_retention_days (0 unless the server has IP collection switched on; sent so older extensions keep working), deletion_epoch, supported_schema_versions, mode. No `pause_allowed` alias. `GET /v1/config` also returns `features: {person_analytics, ip_collection}`, the operator switches, read-only and outside the policy (see below).

Upload envelope and ACK exactly follow CONTRACTS section 5.2. Limits: 100 records, 512 KiB, depth 16. Canonical hashes use shared footprint_contracts. Request before attempt. Valid numeric observations persist even when an estimate is unavailable/pending; client resource amounts are prohibited. Summary filters: start/end are company-local calendar dates (half-open), site/model optional, period week/month/all optional. Ordinary company endpoints reject user/device/IP filters. With sharing on they show organization totals whatever the group size, with no complementary suppression (owner decision of 13 October 2026).

Summary splits: `GET /v1/company/summary` and `GET /v1/admin/summary` add the day, tool and model splits for charts (`sites`, `days` for windows of up to 62 days, `models`). With the query parameter `splits=none` the server does not compute them and returns the same JSON without those three keys; every other field is the same, byte for byte and in the same order, as without the parameter (apart from `snapshot_id` and `generated_at`, which differ between any two answers). Use it on any page that shows no split, because the splits take most of a summary's time and can make the organization summary larger than the extension's 1 MiB answer limit. `GET /v1/me/summary` has no splits and accepts `splits=none` without effect. Any other value, a repeated parameter or `splits` on a conversation or saved-history summary is refused with `unsupported_filter` 422. Behaviour without the parameter is unchanged (15 October 2026).

Admin: `/v1/admin/users`, `/summary`, `/activity`, `/people`, `/health`, `/plan`, `/audit`; role `PUT /v1/admin/users/{id}/role` with role, expected_version integer, idempotency_key UUID, reauth_token; policy `PUT /v1/admin/policy` with expected_version semantic version, timezone, pause_mode, company_sharing, usage_retention optional, idempotency_key UUID, reauth_token; export `POST /v1/admin/exports` with its filters plus idempotency_key UUID and reauth_token, and only the administrator who created an export reads its status or downloads it (others get `export_unavailable` 404); plan change acknowledgement `POST /v1/admin/plan-transition/acknowledge` with transition_id, expected_version, confirmed true, idempotency_key UUID, reauth_token. Deletion preview takes scope (`user`/`range`/`company`), user_id optional, start/end optional; execute takes preview_token, idempotency_key, confirmed true, reauth_token. Role changes, policy changes, exports, plan change acknowledgements, member suspension and reactivation, browser removal, erasure and organization deletion need a reauth_token: request purpose action_reauth with the signed-in email, verify the code, and use the single-use token within 5 minutes. A missing token is refused with 422, a wrong, used or expired one with `reauthentication_required` 403. A role change, policy change, export or acknowledgement retried with the same idempotency_key replays its answer without a new token. Web sessions: an administrator's `__Host-aift` session lasts 7 days from sign-in with no shorter idle limit (`ADMIN_SESSION_SECONDS`); the developer panel's `__Host-aift-operator` session also lasts 7 days from sign-in with no shorter idle limit (`OPERATOR_SESSION_SECONDS`) and is refused at once (`operator_grant_revoked` 403) when its address is removed from the approved list, then deleted by maintenance; `DELETE /v1/auth/session` ends a session at once, and suspension or a role change deletes the target's sessions.

Errors: `{error:{code,retryable,correlation_id,safe_message}}`, no raw request field values or exception bodies. A refused limit (`otp_rate_limited`, `rate_limited`, status 429) also carries `retry_after_seconds`, the whole seconds until the same request can succeed, and the same value in `Retry-After` (20 October 2026; before, `Retry-After` was 60 whatever the limit). Not configured/unverified infrastructure returns an explicit blocked state. No payment checkout is implemented or implied.


## Completed administrative query contracts

By default administrators get organization aggregates only (owner decision of 17 and 18 October 2026). The server enforces this: `GET /v1/admin/requests`, `GET /v1/admin/users/{user_id}/requests/{request_id}`, `GET /v1/admin/network` and `POST /v1/admin/network/access` answer 404, and a `user_id` filter is refused with `person_analytics_disabled` 400 on `/v1/admin/summary`, `/v1/admin/breakdown`, `/v1/admin/people`, `/v1/admin/health` and `/v1/admin/activity`, on exports (also for `report=records`) and on admin recalculations. Aggregates are returned for any number of people, so in a very small organization they can reveal one person's usage.

Two operator settings change this: `person_analytics_enabled` restores the per-person views as they were before 18 October 2026 (one person's summary and breakdown, `requests` per member id on `/v1/admin/people`, the request list and details, the Health list per browser, `last_seen_at` on devices, per-record and per-person exports, one person's recalculation, counts in a person's deletion preview), each showing only usage from the first full day after the switch was first seen on (`person_analytics_since` in summaries and on `/v1/admin/people`); `ip_collection_enabled` restores the collection of connection addresses, and with both on the Network endpoints return. Both are off by default and only the operator can change them; `docs/implementation/CONTRACTS.md` section 8 has the details and what must happen before switching either on.

`GET /v1/admin/activity` accepts `period`, `start`, `end`, `calculation_view` and `method_id`. It returns the organization summary plus `days`, `sites` and `models` splits; the summary and each split carry `active_users` as a count only, never a person or email. A tool's `sites` part also counts its requests without a named model, so the rows by tool and model add up to the whole. With person analytics on, `GET /v1/admin/requests` also returns `person_analytics_since`, the instant its list starts from. `GET /v1/admin/people` returns `used` (people who used AI in the period), `members`, `administrators`, `capacity`, `median_requests`, `average_requests` (among people who used AI), `max_requests` (the most active person's request count, without a name) and `bins` (number of people per request band). `GET /v1/admin/health` returns counts: `browsers_connected`, `browsers_synced_last_day`, `browsers_not_synced_3_days` and `problems` as `[{code, site, browsers}]`; the per-browser list (`items`, `browsers`) comes only with person analytics on.

`GET /v1/admin/breakdown` provides complete SQL organization aggregates, accepts period/tool/model filters (a person filter only with person analytics on) and `group_by=site|model|site_model`. It returns `items` and `next_cursor`; it does not sample request pages. `GET /v1/admin/network` and `POST /v1/admin/network/access` exist only with person analytics and IP collection on. Administrative audit returns `next_cursor`.

Breakdown and audit cursors are signed, filter/tenant bound and expire in 24 hours. They are live keysets, not frozen snapshots: later inserts above the cursor appear on reload, without repeating rows below the cursor. Operator organizations/plans and audit also return bounded `items` plus `next_cursor`; clients treat every cursor as opaque.

## Traceable exports and method views

`POST /v1/admin/exports` creates the organization summary report: `report=summary` with the period/site/model filters and `format=csv`. The per-record report and the per-person filter need person analytics on; otherwise `report=records` or a `user_id` is refused with `person_analytics_disabled` 400, and a per-person export made while it was on can no longer be read. The response includes `export_id`, `status`, `expires_at`, `generated_at`, `metadata`, `row_count`, `byte_length`, integrity and status/download paths. Summary CSV labels calculation view, method ID/hash, environment, selection/profile/boundary, known/unknown coverage, time basis, selected interval, policy and deletion epoch. Maintenance resumes pending jobs.

Downloads check current admin role, retention and deletion epoch for each encrypted chunk. Content-Length and X-Export-Integrity-SHA256/X-Export-Integrity-Algorithm bind completeness to the persisted chunk chain. A revoked, missing or corrupt stream aborts with a fixed safe error and correlated diagnostic; clients must treat length mismatch as incomplete. No private exception text is logged or transmitted.

`GET /v1/methods` returns immutable approved method inventory and the unchanged default method. `POST /v1/me/recalculations` accepts `{method_id,operation_id}`; the admin equivalent is organization-wide unless person analytics is on (otherwise `user_id` is refused with `person_analytics_disabled` 400, and its status for administrators returns only organization-wide jobs). GET the returned job path to inspect pending/completed/failed state. `calculation_view=recalculated` and explicit `method_id` select an available completed current-revision view in summaries/exports; default `original` remains reopenable and immutable. Unavailable future methods remain visible as pending until explicitly approved installation. Original results resolved after installation are separate persisted overlays, never rewritten canonical observations. Alternative calculation does not bypass company suppression.


Session restoration uses `GET /v1/auth/session` or `/v1/operator/auth/session`, with exact authorized Origin and no-store. The returned CSRF token is stable for that session. Read activity updates an independent timestamp, avoiding whole-session JSON overwrite during concurrent reads.

`GET /v1/config` returns the direct policy object. It reads without the organization's lock and takes it only when it must save a changed policy version or record that this installation was offered a new one, so it no longer waits behind an upload or the maintenance worker. Installation `POST /v1/config/acknowledge {policy_version}` returns stable `acknowledged_at`, `effective_from`, `enrollment_era_id` and `device_id` alongside the version. Persist the receipt before labeling subsequent captures; queued dispatch timestamps are checked against immutable capture-era policy history. Same-device reconnect retains historical closed-era acceptance.

Deletion previews return pending state, counts_complete and status path. A preview or job that names one person (`user_id`, for scope `user` or `range`) says what will be deleted in `deletes` and returns no record counts and no date range of that person's records (counts and contribution dates are null or empty, `counts_shown` false), unless person analytics is on and none of the counted records predates the switch; a range or company preview without a person keeps its counts. A maintenance tick or authenticated `POST /v1/admin/deletions/previews/{id}/advance {}` advances one bounded page. GET status is read-only. Final execution is rejected until the complete preview is available. Signed deletion changes return page epoch/current epoch/has_more; clients drain all pages before uploading queued work. Independent device erasure receipts never imply that an offline device already erased its local storage.

Registration-only `GET /v1/public/deployment` returns exactly `{mode, hosted_domain, registration_origin}`; hosted_domain is null in self_hosted mode. It is no-store, contains no credentials and rejects other origins.


## Retry and identity invariants

Deletion `idempotency_key` identifies an operation only within its tenant and actor. The response `job_id` is a distinct deterministic scoped UUID; use the returned job/status path rather than constructing it from the caller key. Independent tenants or actors may safely use the same key. Durable erasure markers remain immutable and restore replay preserves their tenant scope. The common persistence helper rejects changing a row's tenant or owner.

OTP verification requires a persisted `verification_id` per challenge. Retrying the same challenge/code/ID before the original challenge expiry replays the same encrypted result and cookie; it creates no extra session or organization. A different ID or invalid code cannot redeem a consumed challenge. Replay checks current session expiry, membership/operator authorization or one-use reauthentication proof. Logout/revocation prevents replay from resurrecting credentials. Registration replay recovers the same registration session and bootstrap destination.

Request site/provider identity is immutable. Response observation may promote a provisional conversation key to the canonical key; the current request projection and its owner-scoped child projections change atomically. Historical numerical payloads remain unchanged. Observed model corrections update their own indexed model and apply old/new contribution deltas. Reconciliation record reads honor retention immediately, before asynchronous physical cleanup.

Summaries expose `observed_search_operations` as the known explicit invocation sum, alongside `search_known_request_count` and `search_unknown_request_count`. Unknown search coverage is not zero. Token series retain `measurement_group` (evidence/profile), compatible resource series retain `method_group`, and both expose reversible `reason_counts`, partial and unvalidated counts. `media_counts` separately labels requested image operations/outputs, executed operations, provider returned outputs and observed artifacts. These rows have their own scope/unit and must not be added across categories. `image_references` contains only separately labeled GPU reference quantities, never ordinary resource totals. CSV retains these groups and labels. (Superseded on 13 and 14 October 2026: member-company responses no longer suppress groups with fewer than five people; members see organization totals however few people use AI. See CONTRACTS.md 6.4.) Original and recalculated member-company responses used to suppress the entire response if any disclosed constituent day/site measurement/profile/reason subgroup had fewer than five people, including complementary totals.

Caller-ID storage audit: registration operations bind registration origin plus the email identity (see below); OTP dispatch/resend bind origin/purpose/challenge; OTP verification binds origin/challenge/code/verification ID; connection creation binds tenant/operation plus payload hash and proof; refresh/disconnect bind existing credential proof and operation; role changes bind tenant/actor/operation; operator assignments bind operator identity/origin/path/operation; deletion binds tenant/actor/operation; recalculation binds tenant/actor/operation. Canonical revisions and upload receipts bind tenant/owner/kind/record/revision. Domain approvals and plans are intentionally shared versioned administrative identities, protected by current operator authorization and explicit version checks. Server-issued random IDs identify sessions/devices/grants/exports and are never accepted as authority without tenant/owner/proof checks.


## Count disclosure and operator audit attribution

Member-company suppression also covers each nonzero outcome, canonical/unresolved request count, confirmed/unconfirmed attempt count, pending/nonpending estimate count, resource-known/resource-unknown count and explicit search count. These checks apply to constituent company-local day/site groups, not only the combined date range. Logical complements of outcomes, measurement status counts and reasons are protected too. A subthreshold group suppresses the entire member-company payload, including its complementary totals and derived active-user/installation counts. Administrators retain the complete normative fields. Original activity checks use SQL distinct-owner aggregates over indexed rollup bounds; recalculated views use the same definitions during their existing record stream. No extra retained-request scan is introduced for these checks.

Operator audit rows now contain the authenticated operator's pseudonymous session-owner UUID as `actor`, with `actor_kind: "operator"`. Different allowed operators therefore have distinct authorship. Client bodies cannot supply or override this authority. Old rows with literal `actor: "operator"` remain visible as legacy records; their historical identity is not fabricated. Automatic registration consumption records its verified registering member as actor and retains the approval reviewer reference in details. Actual maintenance actors remain `system`.


## Entitlement conflicts, cancellation and atomic replacement

Current organization detail and admin plan responses include `entitlement_generation`. New ordinary assignments and exception grants reject with `409 entitlement_conflict` while an active/revoking exception or nonterminal transition exists. Entitlement decisions increment this generation independently of service-status versions. Transitions bind their generation and the effective plan/capacity/retention/timezone snapshot. Maintenance never applies a cancelled, superseded, mismatched or ambiguous transition. A legacy transition without a verified baseline is `review_required`; it does not silently shorten retention.

Transition rows expose `status` (`pending`, `review_required`, `cancelled`, `superseded`, `applied`), `version`, `company_version`, `current_entitlement_generation`, `operator_can_cancel` and `operator_can_review`. The operator uses:

- `POST /v1/operator/organizations/{company_id}/transitions/{transition_id}/cancel`
- `POST /v1/operator/organizations/{company_id}/transitions/{transition_id}/review`

Both require `{expected_version, expected_company_version, reason, confirmed:true, idempotency_key, reauth_token}`. Cancellation is terminal and invalidates prior acknowledgements. Exception reversions cannot be cancelled by themselves (`409 exception_reversion_required`). Review rebinds a nonterminal transition to the current effective policy, recomputes its retention preview and resets acknowledgement. Fresh admin acknowledgement is required only for net-shortened retention. Outcomes return the current transition row. Admin acknowledgement rejects terminal or unreviewed baselines. All decisions are audited with the authenticated operator pseudonym and a nonblank reason; worker application is attributed to `system`.

`POST /v1/operator/organizations/{company_id}/exceptions/{exception_id}/replace` is an explicit immediate-only replacement with an existing selected plan. Body: `{expected_version:<exception version>, expected_company_version, expected_transition_version:<reversion version>, expected_entitlement_generation, plan_id, plan_version, reason, confirmed:true, idempotency_key, reauth_token}`. Future `effective_at` is not accepted by this endpoint. It atomically supersedes the exception and old reversion. Equal/longer retention applies directly, with no intermediate lower-retention policy. Net shortening from the current effective policy creates a new unacknowledged transition and holds the current limits until its preview is acknowledged. Response: `{status:assigned|retention_transition_pending, exception_id, superseded_transition_id, transition_id:null|UUID, version:<company version>, entitlement_generation}`.

Cancelling a pending net-shortening replacement restores its former dated exception and a freshly unacknowledged reversion; the response includes `restored_reversion_id`. The confirmation must explain this restoration. The operator can then explicitly replace that exception with a different selected plan, without briefly applying its old lower-retention base. Other pending transitions must first be cancelled or reviewed; ambiguous future combinations are rejected.

Existing `DELETE /v1/operator/organizations/{company_id}/exceptions/{exception_id}` now additionally requires `reason` alongside `expected_version`, `idempotency_key`, `reauth_token` and optional `transition_acknowledgement`. It cannot bypass a net-shortening admin acknowledgement. Transition versions advance on review, acknowledgement, cancellation, acceleration and application. Clients refresh the current row after every action and preserve the operation ID while retrying. Ordinary assignment dates already in the past take effect no earlier than server receipt time, so a new shortening preview cannot use a backdated cutoff.

Transition rows additionally expose `current_entitlement` and `target_entitlement`, each `{plan_id, plan_version, capacity, retention_months, timezone}`. `base_entitlement` is the historical scheduling snapshot; `current_entitlement` is live. `target_entitlement` is null if its immutable plan is unavailable. Admin acknowledgement UI displays the target capacity and retention with the preview, and does not guess unavailable target values.


Verified pending transitions expose `acknowledgement_required`. It is true only when the target shortens current effective retention. A false value means automatic application on the first maintenance tick at or after the effective/expiry time; `acknowledged` remains false unless an administrator actually acknowledged it. Capacity-only exception reversions and scheduled retention upgrades therefore do not wait for unnecessary admin action. `review_required` blocks both kinds regardless of this flag. Revalidation recomputes net shortening against the live policy and resets acknowledgement; cancelling a replacement recomputes the restored reversion's requirement too. Client copy prioritizes lifecycle status, then this explicit flag, rather than treating every unacknowledged row as blocked on an admin.

Cancelling a reviewed replacement restores the former exception's effective capacity/retention and base-plan identity before binding and classifying its reversion. This remains correct when a restored legacy deployment had changed the current policy before review; a previously nonshortening replacement does not make the restored exception's shorter reversion automatic.

## Extracted document text and schema 1.2.0

`GET /v1/config` advertises both `1.1.0` and `1.2.0`. A 1.2 batch accepts mixed exact historical records; a 1.1 batch remains 1.1-only. New 1.2 requests require `documents.extracted_text: null | ExtractedFileTextComponent[]`. Unassociated local extraction stays null. Components are bounded, random request-scoped UUIDv4 identities with origin, extraction profile, nullable page count, a specialized `extracted_file_text` token measurement, and explicit missing coverage. See CONTRACTS section 11. No ordinary token field gains an extracted-file scope.

Summary responses add `file_text` and `file_text_coverage` without changing existing quantities. `file_text` rows contain:

```json
{"quantity":"extracted_file_text","value":"123","unit":"tokens","scope":"extracted_file_text","additive":false,"measurement_group":{"origin":"new_upload","extraction_profile_id":"local-file-text-utf8-pdfjs6.3.289-opc-v1","evidence":"heuristic_estimate","profile_id":"o200k-base-4.0.0-reference"},"applicable_count":1,"contributing_component_count":1,"unknown_count":0,"partial_count":1,"unvalidated_count":1,"reason_counts":{"tokenizer_mapping_unverified":1},"missing_counts":{"provider_processing":1,"ocr":1}}
```

An all-unknown group's `value` is null. Aggregate integral strings can exceed the individual BIGINT Counter bound; do not convert them through JavaScript Number. Count fields in component series follow existing numeric series denominators. `file_text_coverage` is `{observed_request_count:"1",unknown_request_count:"0",scope:"extracted_file_text",additive:false}`. Empty observed component lists and unknown coverage differ. Suppressed member-company summaries omit all quantities as before. Original and recalculated views apply identical file disclosure rules.

Summary CSV adds the file rows separately with `contributing_component_count`, `missing_counts`, `additive` and full `measurement_group`, plus file coverage count rows. Their `time_basis` is `dispatch`. Request detail and records CSV (with person analytics on) include exact versioned documents, with unchanged original hashes. No file quantities enter regular token/resource totals.

Migration head is now `0005`. Upgrade before starting the new API/worker; existing populated companies report rebuilding until bounded projection reconstruction completes. Old exports are cancelled. Historical observations, revisions, ACK hashes and original estimates are not modified. A binary requiring an older guard is incompatible and must remain stopped.

(Superseded on 13 October 2026, as above: the five-person rule below no longer applies to member-company summaries.) Schema 1.2 file disclosure amendment: migration `0006` supersedes the projection format from `0005` and requires guard 6. Derived rollups retain private request-presence counters for each file measurement group. Ordinary company summaries verify contributors to both group presence and absence against the disclosed day/site request population. Thus five people with components plus one person with an observed empty list cannot disclose a singleton complement, even though the component group itself has five people. Missing metadata fails closed until bounded rebuilding; no extra counters appear in the public DTO. Original/recalculated paths use the same rule, and admin scope remains unaffected. Telemetry versions and raw hashes do not change.

## Loaded historical messages, schema 1.0.0

Migration `0008` and guard 8 add the separate numeric history family after `0007` scoped thread relations. The [history contract](../../docs/implementation/CONTRACTS.md#14-numeric-history-observed-while-the-user-loads-a-conversation) defines the strict DTO, date bases, overlap rules and retention decision. Live observation schema versions and execution totals do not change.

- `POST /v1/me/history` requires an active authenticated installation and current deletion epoch. Submit at most 100 numeric messages and 256 KiB per page. Ordered receipts return the message key, numeric payload hash and `applied`, `duplicate`, `conflict` or `erased`. Only matching queued hashes may be acknowledged. A failed or malformed response keeps the queue intact.
- `GET /v1/me/history/{conversation_key}/summary?period=all` returns `{history, deletion_epoch}` independently of recorded live conversation availability. Member, company and admin summary responses also include a separate `history` projection. Loaded prompt/response counts include conflicts and proven live matches; imported contributions exclude both. Unresolved overlap never adds to live totals.
- `GET /v1/me/history/export` provides up to 100 numeric observations per page, with optional `conversation_key` and opaque `cursor`. Each record retains original/current observations and assessments, source date/basis and numeric payload hash. Standard admin records CSV also includes historical rows with `record_kind=history_message` and original/current assessments.
- Deletion previews expose separate `historical_message_count` and `undated_historical_message_count`. Explicit erasure, stable tombstones and protected restore replay cover history. Hosted live age cleanup preserves imported history, including old and undated messages. Legacy ambiguous tombstones remain conservative.

Personal history stays local and is never backfilled on Connect. Newly observed connected messages use import time for enrollment ownership and their reliable source time for date selection. No raw message text or raw provider identity enters these APIs or exports.

## Parallel-engine compatibility and self recalculation

Migration `0009` requires schema guard 9 and adds immutable numeric source/result overlays. Live and historical ingestion support the packaged original and native EcoLogits methods, without changing observation bytes. Config and method inventory advertise result schemas `1.0.0` and `2.0.0`; original-only historical summaries remain `1.0.0`, while new resource rows require summary `2.0.0`.

An authenticated installation uses `GET/PUT /v1/me/estimation-selection` to persist its local choice and schedule bounded self-scope recalculation. PUT requires `{preference, selection_revision, method_id, method_hash, operation_id}`. The response contains `{selection, compatibility, recalculation}`. Readiness, exact retries, scope isolation, generation guards and pending compatibility are documented in [ECOLOGITS.md](ECOLOGITS.md). Existing manual self/admin recalculation paths remain available, with their existing role boundaries.

Recalculated views and exports include history and retain originals. Per-record raw ranges remain intact; summary groups add midpoints with `value_kind: "midpoint_sum"`, add every record's endpoints into `scenario_low`/`scenario_high` (scenario sums; null for rollups written before 17 September 2026) and keep `interval_kind` null. A selected installation defaults to its completed recalculated view on its own summary/history export reads; callers can explicitly request `calculation_view=original`. Missing/incompatible methods remain pending instead of selecting an alternative implementation.

Canonical request aliases can add `source.canonical_request_binding` to a live envelope. Its domain-separated relation hash binds the actual canonical request and the original attempt's observed request ID. Only the server's authenticated alias lookup can authorize this relation. Client flags/hashes are not evidence of a relation, and raw observations are never rewritten to manufacture one.

## Members, browsers and the end of an organization (14 October 2026)

**Email identity (migration `0014`).** Membership, seats, code limits and erasure key on `email_identity`: the local part in lower case and without a `+tag`, the domain normalized. `Bob@x.org`, `bob@x.org` and `bob+ai@x.org` are one member. A code never goes to a variant: for an existing member it goes to the address the member is stored with (a separate `bob+x@` or `Bob@` mailbox on a server without subaddressing or with case-sensitive local parts must not receive a code that acts as `bob@`); a new member is mailed and stored at the typed address. Developer sign-in ignores only case, never a `+tag`, and mails the configured address. RFC 5321 allows case-sensitive local parts, but no mainstream provider uses them. Migration `0014` moves each stored identity to its new key and requires guard 14. It needs the production settings file (encryption and lookup keys) when identities exist. If two active members of one organization share an identity, or an erased member's row already holds it, the migration stops without changes and lists the member ids; resolve them with the previous release, then run it again. An erased member's row keeps its old key and still blocks that exact address.

**Code emails.** Sign-in and connection codes for a domain without an active organization are not mailed. The request is counted and answered exactly as a sent one: same status, body, stored challenge and a delivery step of similar duration (and the same failure state while real mail is failing). An unsent code checks but never uses the shared daily budget (`global_mail_daily`). Registration codes may use at most `registration_mail_daily` (default 50) of it, plus 5 per domain per day and 3 per network per 15 minutes (10 per day). Every code counts against 10 per network per 15 minutes, 30 per day, and 5 per recipient identity per 15 minutes (20 per day).

**Browsers and suspension.** Administrators use `GET /v1/admin/users/{user_id}/devices` (`device_id`, `browser_family`, `status`, `first_seen_at`, never an IP address; `last_seen_at` only with person analytics on), `POST /v1/admin/users/{user_id}/devices/{device_id}/revoke` with `{reauth_token}`, and `PUT /v1/admin/users/{user_id}/status` with `{status: "active"|"suspended", expected_version, reauth_token}`. A removed browser and every browser of a suspended member answer `403 enrollment_revoked` on their next call and refresh. A suspended member cannot connect (`member_unavailable`) and keeps their data; an administrator cannot suspend themselves (`409 self_action`). A removed browser connects again as a new browser after a new email code. Revoked refresh tokens are kept 30 days, like replaced ones, then deleted.

**Ending an organization.** `POST /v1/admin/organization/deletion` with `{reauth_token, confirm_name}` schedules deletion in 7 days and stops the organization at once: members get `403 service_suspended`, administrators can still sign in, read `GET /v1/admin/organization/deletion` and cancel with `DELETE` until then. `GET /v1/auth/session` reports `organization_status`. The worker then deletes every row with the organization's tenant key in bounded pages, plus its completed registration, and keeps one developer audit row `organization_deleted` with the internal id and two dates. Request, cancellation and deletion are written to the deletion journal, so `replay-journal` after a restore repeats them.
