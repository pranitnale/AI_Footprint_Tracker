## 3. Organization registration

### 3.1 Registration form

Collect legal/display company name, website, approved employee email domain, country, registering administrator's work email, registering person's name and role, and acknowledgement that they are authorized to register and accept the disclosed service terms. These registrant contact details are separate from ordinary employee usage. A CEO name is not required merely to appear more verified: the user gave it as an example of basic information, not an identity oracle. Do not collect government identity documents or unrelated employee information.

Display exactly what verification proves: control of the work mailbox. It does not prove company ownership, legal existence, a CEO's identity or authority to represent the organization. The owner rejected customer-domain DNS verification. Authenticate the project's own mail-sending domain and hosting DNS normally; that is a different requirement. Provide an operator dispute/review path for impersonation or conflicting domain claims. Do not promise a verified-company badge from a form and OTP alone.

Use one approved work domain initially. Normalize domains through a tested IDNA library to lowercase ASCII and match the complete domain after `@`, not a substring. Do not accept lookalike suffixes, arbitrary subdomains or a free-mail domain as a company's own work domain. Keep a reviewed/versioned free-mail-domain exclusion list and a visible manual-review path for legitimate exceptions. This is eligibility filtering, not proof of corporate authority.

Normalize surrounding whitespace and the domain of an email. Preserve the local part and do not apply consumer-mail dot removal, plus removal or universal case folding. Store/display the canonical address used for enrollment. Additional case/alias equivalences require verified ownership and explicit account-linking policy, not silent merging. Use a tenant-scoped keyed lookup value for uniqueness and an encrypted email value for delivery/admin display. Keep auth keys separate from usage/IP keys. Ordinary usage payloads never contain email.

### 3.2 Organization key and provisioning

**Rewritten 13 October 2026 (owner decision).** Registration does not ask for an organization address. The server generates an internal organization key that is never shown and is not a served address; all hosted organizations are served at `https://aifootprinttracker.com`. Unicode display names are allowed. The organization's identity for members and administrators is its name and registered work domain.

Registration states: `draft -> verification_pending -> verified -> provisioning -> active`, with `expired`, `rejected` and `provisioning_failed` terminal/retry states as appropriate. Store a draft ID, idempotency key, canonical domain, form version and disclosure acknowledgement. Development default: unverified drafts expire after 30 minutes; a fresh attempt after expiry must recheck the domain and verification. A consumed OTP cannot be reused to take over a different draft.

Only after successful registering-admin OTP verification may one transaction create the organization, first user/admin membership and provisioning job. Enforce the one-hosted-organization-per-domain rule with unique constraints or serialized domain claims, not only application checks; a second organization on the same domain needs an audited developer exception. Retrying a committed registration returns the same organization/job to the same verified registration principal. It never creates a second company/admin. Provisioning failure retains that identity for retry and does not label the organization ready.

Hosted operation needs DNS and TLS only for the fixed hosts: the registration address and the developer panel. Creating an organization creates database state, not routing or certificates. The actual provider and DNS credentials are deployment choices, not browser-side code.

Self-hosted setup uses the same verification/role/data contracts with one configured tenant at its own origin. That origin needs its own domain or subdomain; it is not served under our domain and does not register with the hosted operator.

### 3.3 First-admin transition to the tenant origin

**Rewritten 13 October 2026 (owner decision).** Hosted registration no longer needs a transition: the dashboard lives at the registration address, so verification sets the `__Host-aift` session there directly and returns the destination `/admin`. The bootstrap below applies only to self-hosted servers, whose registration host and tenant host are separate origins.

Host-only registration cookies do not authenticate the separate self-host origin. Implement a dedicated short-lived bootstrap so the verified registrant reaches `/admin` without entering a second OTP:

1. After provisioning, navigate to that tenant's fixed `/auth/bootstrap/start` route with the non-authorizing registration locator. The tenant sets a Secure/HttpOnly short-lived bootstrap nonce cookie and stores a pending transaction bound to its exact origin and that registration. It redirects to the configured registration origin's fixed authorization route with an opaque state locator.
2. The registration origin requires the still-valid verified registration session, the same draft/first-admin identity, an active provisioned tenant and a matching pending transaction. It creates a random one-use bootstrap grant valid for 60 seconds, bound to tenant audience, user, transaction and nonce. A guessed draft/state does not grant access.
3. Deliver that grant through a `no-store` server-generated form POST to the exact tenant `/v1/auth/bootstrap/exchange` endpoint, not a query string, store link or extension message. This endpoint is the sole form-body exception to strict JSON APIs: accept only `application/x-www-form-urlencoded`, at most 4 KiB, with exactly `registration_id`, `state`, `bootstrap_grant`, each a bounded opaque value of at most 128 ASCII characters. Reject duplicate/extra fields, multipart, malformed encoding and other content types. This narrowly scoped web-login grant exists only on the trusted registration page. Use a restrictive form-action policy, no third-party script/analytics and no logging of the body. It is not an extension or reusable admin credential.
4. The tenant verifies the nonce cookie, grant/state binding, exact permitted registration Origin, current membership role, expiry and unused state atomically. Set a fresh host-only web session, consume the grant and return a `no-store` 303 redirect to `/admin`. Never accept arbitrary return URLs or an organization login as platform-operator authority.
5. If a response is lost or the grant expires, restart the bootstrap from the authenticated registration session rather than consuming the original OTP again. Supersede the prior pending transaction and revoke any orphan bootstrap session created for it. If that registration session has itself expired, use the normal administrator OTP login. Test wrong-browser nonce, swapped tenant, replay, expiry and lost-response paths.

The bootstrap cookie/transaction has a proposed five-minute lifetime. Sibling subdomains remain untrusted outside this exact transaction. Do not replace this protocol with a wildcard-domain session cookie.

## 4. Email codes: administrator website sign-in and member connection

**Rewritten 13 October 2026 (owner decision).** Both flows use the same Brevo code rules below; only administrators use the website.

1. An administrator opens `https://aifootprinttracker.com` (or a self-hosted server's own origin) and enters a work email. A member enters the work email in the extension's Connect dialog instead (Section 5).
2. At the hosted origin the backend selects the one active organization whose registered work domain equals the email's domain; a self-hosted server uses its one organization. It issues a purpose/recipient-bound OTP challenge (`login` on the website, `connect` from the extension) whether or not an organization uses the domain, so the response cannot reveal which domains are customers. Free-mail domains are refused at once with `work_email_required`. Brevo sends the minimal code message. Sending errors remain honest.
3. The user submits the code once. The server atomically consumes the valid challenge. Only then may it answer `organization_not_found` ("No organization uses this work email domain"), with advice to check the work email, ask the administrator which work email the organization was registered with, or register the organization.
4. Website sign-in: an existing active administrator gets a web session and the destination `/admin`. Anyone else gets `admin_required` ("Only administrators sign in on the website. Members connect from the AI Footprint Tracker browser extension."), no session and no new member. The initial verified registrant became admin during organization creation. A matching work domain, guessed URL, supplied role or verified member code alone never creates admin access.
5. Extension connection: the server creates or retrieves the same tenant-scoped identity as `user` and continues as Section 5.2 describes. Concurrent first connections with the same canonical email must resolve to one membership. There are no member web pages, and there is no admin link or second admin login inside the extension.

Use Brevo's specified six-digit cryptographic code, five-minute lifetime, five invalid attempts and 60-second resend cooldown. Reuse one challenge dispatch for an ambiguous send retry; resend deliberately replaces the old code. Follow the full [Brevo setup](BREVO-PRIVACY-SETUP.md), including keyed code storage, encryption of short-lived send queues, delivery status, no tracking pixels/rewritten links, one-month logs, no previews and account-wide quotas. A Free-plan quota is shared by all tenants, not multiplied by tenant count. Production delivery is gated on actual account approval and tests, not this plan.

Proposed extra application limits: at most five new code dispatches per recipient/tenant in 15 minutes and 20 in 24 hours; global and tenant budgets must fit the actual mail allowance, with separate configurable network abuse limits that account for shared office NAT. Return a safe retry time. Do not use one office IP as employee identity or silently lock out the whole company after one failed user. Final abuse budgets are deployment configuration, versioned and load-tested.

Web sessions are separate from extension credentials. Proposed defaults: `__Host-` prefixed Secure/HttpOnly cookies, `Path=/`, no `Domain`, SameSite=Lax plus explicit Origin/CSRF validation for mutations. Decided lifetimes (owner decision of 14 October 2026): an organization administrator's session lasts 7 days from sign-in with no shorter idle limit (`ADMIN_SESSION_SECONDS`), and the developer panel's session also lasts 7 days from sign-in with no shorter idle limit (`OPERATOR_SESSION_SECONDS`). Because of the longer administrator session, role changes, policy changes, exports, plan change acknowledgements, showing connection addresses, suspension and reactivation, browser removal, erasure and organization deletion each need a fresh single-use email code. Because of the longer developer session, a developer's change of an organization's service state, plan assignment, exception grant, revocation or replacement, plan transition cancellation or review, domain approval and contact request deletion each need a fresh single-use code sent to the configured developer address; removing the address from the approved list ends its sessions at once. Apply the same cookie naming/scope rules to registration, bootstrap and isolated operator sessions. Reject ambiguous duplicate authentication-cookie names rather than picking the first/last. Rotate on login and role change; check current membership status/role on privileged requests, exports and background jobs. A sibling origin is not trusted just because the browser treats it as same-site. No wildcard-domain authentication cookie. Test parent-domain cookie injection and target-browser prefix enforcement.

Organization authentication is OTP only. Do not add a password, mandatory authenticator, or repeated OTP merely to enter `/admin` after the single successful login. Destructive reauthentication or expired-session renewal uses another email OTP of the correct purpose when required by Contracts, not a new factor. Short-lived reauthentication can authorize the specific deletion/device-revocation action without changing an employee into an admin.

## 5. Connecting an installed browser

### 5.1 User flow and installation boundary

**Rewritten 13 October 2026 (owner decision).** Every member installs the same public store package. A store link cannot safely contain a reusable company credential or silently customize a signed package. After installation the member opens the extension, chooses Connect organization and enters their work email; administrators give members these instructions from the admin dashboard. By default the extension connects to the hosted service at `https://aifootprinttracker.com`. A small secondary option, "Your organization runs its own server?", asks for a self-hosted server's HTTPS address instead. Managed deployment may preconfigure that address, but it does not bypass mailbox authentication or the required collection disclosure.

The member enters the six-digit code from the email in the extension. The extension then shows "Connect to {organization}?" with the organization name, data collected and pause policy before activation, and a single explicit confirmation binds this installation to the verified identity. No website page, web session or approval tab is involved. Keep local-only use available until this succeeds. Never say connected just because a browser tab or store page opened.

### 5.2 Installation-bound handoff

Implement an extension-initiated, email-code-authenticated connection, not arbitrary webpage-to-extension credential messages. Packaged-browser proof is still required:

1. The extension requests the browser's permission for the chosen origin only and calls `POST /v1/connections/otp/request` with the work email and a dispatch ID. The response is a `connect` challenge result (`challenge_id`, delivery state, expiry, retry time) and does not reveal whether an organization uses the domain. The extension can resend after the retry time through `POST /v1/auth/otp/resend`.
2. The extension creates a cryptographically random 256-bit verifier and persists a pending connection record in trusted extension storage. It calls `POST /v1/connections` with the verifier's SHA-256 challenge, declared browser family, client protocol version, an operation ID, the challenge ID and the entered code. The server checks the code (five attempts, expiry, single use), retrieves or creates the membership as `user` (capacity enforced) and creates a random connection ID in state `verified` with a ten-minute expiry. That ID is a locator, not a credential. The response carries the organization name, public origin, current policy and deletion public key. `organization_not_found`, `member_unavailable` and `capacity_reached` are possible only at this step, after a correct code. Never put the verifier, code, access or refresh token in a URL, DOM message or log.
3. The extension shows the organization name and connection disclosure, and the user confirms explicitly. There is no web approval, polling or display phrase: the email code already proved who is connecting.
4. The extension exchanges the verified connection using the verifier, a persisted `exchange_id`, the `policy_version` it showed and `disclosure_acknowledged: true`. In one database transaction, check origin, proof, expiry, active tenant/user, current policy (a changed one returns `policy_changed`) and one-use state; create exactly one installation and its credential family for a new browser, or renew the original installation under Section 5.4. The membership verified by the email code, not a body-supplied user ID, selects the user.
5. Return scoped access/refresh credentials, the organization name, current policy and user key material. The same valid proof and exchange ID can retrieve an encrypted cached result after a lost response for up to 24 hours, unless revoked/deleted. A different exchange ID cannot redeem the consumed connection. The original token expiries do not restart on retrieval. The client durably stores credentials before clearing pending state and only then displays Connected.
6. All normal consumption requests use the narrow installation credential, not the web cookie. Content scripts/page code receive no credential. Each installation gets its own refresh family, restricted reconnect proof and independent deletion-receipt capability. Existing Contracts refresh replay/rotation and erasure rules apply unchanged.

Prove optional-host permissions, trusted extension storage and page isolation on Chrome, Edge and Firefox. The flow does not depend on a Chromium-only website messaging API. It still needs browser-specific lifecycle/security tests; the development browser's capabilities do not establish packaged-extension support. Validate an entered self-hosted address as an exact HTTPS origin. Reject arbitrary redirects, downgrade to HTTP, credentials in origins, malformed hosts and cross-origin token delivery. Development localhost exceptions must be build/config scoped and cannot silently ship as permissive production defaults.

The extension's pending states are `code_sent` and `verified`. Server state transitions are `verified -> approved -> consumed` (approved and consumed in the exchange transaction), or `denied`/`expired`/`revoked`/`cancelled`. Store challenge, tenant, owning member, expiry, acknowledged policy, exchange ID and credential-family association. A user can cancel a pending connection locally and server-side. Restart resumes the same pending ID, not a duplicate user. Switching to another server origin cancels the old pending flow before beginning another.

### 5.3 Same person across installations

The same verified canonical work email in the same tenant retrieves the same stable internal user ID on all supported browsers and machines. Chrome and Edge on one laptop plus Firefox on another means one user and three installations, not three people or proof of two physical machines. No existing device needs to be online, and no recovery phrase is required for an ordinary connection. Reinstalling and connecting again with an email code adds an installation to the same user; it does not revoke healthy other installations unless the user/admin explicitly chooses that action.

Each tenant has an independent identity namespace. Do not join accounts across companies using email, IP or AI-provider login. Never merge different email addresses merely because they might be aliases. Deleted users are not resurrected by old login/handoff retries. Deliberate later rejoining, if allowed by company policy, creates a new identity after a fresh flow and must not restore erased records or old keys.

### 5.4 Reconnect an existing installation without changing record ownership

An installed profile that still holds an old organization queue must be able to renew that **same installation**, not upload its records using a new device ID. At initial exchange issue a random 256-bit `installation_reconnect_secret`, store its hash separately server-side and keep the value only in trusted extension storage. It cannot read/upload/refresh/approve anything by itself. It is an internal proof, not a phrase the employee must save or enter.

For reconnection, the extension starts the ordinary connection with `resume_device_id` and the reconnect proof in the protected request body. It still requires a fresh email code verified for the member who owns that installation. A device ID unknown in the organization the code selects is ignored and the browser connects as a new installation; a known device with a wrong proof or another owner is `connection_denied`. The server binds the pending connection to that device, checks proof and status, and exchange issues a new credential family **for the same device ID**, rotating the reconnect proof atomically. Idempotent lost-response recovery returns that same rotation result. A different user, tenant or browser lacking the proof cannot reclaim the device.

Credential expiry or an explicit self-disconnect permits this flow for an active member. Administrative/security revocation does not: it requires an authorized admin reactivation or a new permitted installation, without transferring the revoked device's queue. Deletion permanently invalidates its reconnect proof. Never reuse the deletion-receipt credential for reconnection. Ordinary reinstall after storage loss lacks the proof and creates a new installation for the same user; it cannot revise records owned by the lost installation.

Keep installation enrollment eras server-side. Token expiry alone does not end an acknowledged capture era; explicit disconnect closes it when received, and reconnect creates a new era for the same device. On renewed upload, allow records from an earlier valid era of that original device only if still within retention and not erased. Do not treat those records as pre-enrollment merely because they predate the new credential family. New activity during a local-only/disconnected era cannot be reassigned to the organization. After renewal, synchronize current deletion/retention state before draining the old queue. This preserves both original-device revision ownership and legitimate offline recovery.

## 6. Local-only and organization data boundaries

Maintain a personal local namespace and distinct organization/enrollment-era namespaces. Personal counting produces no network outbox. Personal periods use a locally configured IANA timezone, initially the browser's local timezone; time-zone changes re-bucket local data explicitly. Personal multi-device aggregation is not promised without a separate user-managed import/export feature, which is outside first release.

Connecting starts an organization capture era after the verified email code and the acknowledged disclosure. Earlier stored personal history is not uploaded. Newly observed provider history can produce separate numeric imports owned by the current approved importing user and conversation, including source dates before enrollment. This does not establish the original author's identity or create observed execution records. Old text can also inform the next request's local active-context estimate. After disconnect, new activity is local-only. Existing organization records stay attributed to the old organization, never copied into another organization's outbox or merged into personal totals automatically.

Loaded counts include all deduplicated available prompts/responses in the stated branch scope. Imported token/resource contributions exclude proven matches to live records and conflicting records; matched and conflicting messages remain visible in loaded counts. Unresolved overlap is shown separately and is never automatically added to live totals. Source dates retain message-, entry- or turn-creation meaning; unknown dates are neither import dates nor zeros. Imported estimates retain their recorded method/profile and remain explicitly partial even after a reviewed first-available-request boundary is reached.

Disconnect stops new company capture/uploads, revokes the installation when reachable and marks any remaining queue held for that original identity. Show pending count and an explicit choice before discarding unsynced numerical records. Reconnecting the same approved identity may resume still-eligible data only after policy/deletion reconciliation; connecting another organization cannot. A company deletion or retention expiry may purge affected records under the previously disclosed policy even while they are held. Never preserve data indefinitely against an applicable erasure instruction.

Numerical request/attempt data includes opaque IDs, website/model evidence, time, token scopes, outcomes, allowed modality metadata, estimator versions/assumptions and coverage. No prompts, answers, thinking text, filenames, document contents, titles, URLs, embeddings, provider-account identities or content hashes go to the server. Temporary text processing is in memory only. Server-observed IP history and encrypted work-email mappings live in separate restricted stores. Usage is identifiable to company admins through the email mapping, not anonymous.

## 7. Plans, limits and retention

### 7.1 Entitlements

Model plans as immutable versioned configuration: plan ID/version, member capacity, usage-retention months or explicit indefinite mode, effective time and feature flags. Organization assignment selects a plan plus any dated operator exception. Every exception records organization, exact overridden fields, reason, author, effective/expiry times and audit reference. The operator can grant free access or extended retention without entering a payment record. No original-source license restriction depends on a hosted plan.

Use the pending 50-person definition only as a development fixture until answered. Under the provisional enrolled-member interpretation, count active tenant memberships including admins once, regardless of installations or activity; pending/unverified signups do not consume seats. Lock the entitlement/membership allocation when two people try to take the last seat. Existing member sign-ins or new installations for that member do not consume another seat. Capacity failure shows the organization limit and safe contact path without granting a partially working enrollment.

If an override expires with more current members than the lower limit, block new memberships/reactivations, show the over-limit state to admins/operator and preserve existing members' tracking and access. Do not choose employees to delete, demote the last admin or discard usage as a billing action. Further restrictions require an explicit product decision. Self-hosted operation has configurable operational limits, not mandatory enforcement of the hosted free tier.

### 7.2 Usage retention

Hosted free and self-hosted live request families are kept until an administrator deletes them (owner decision of 11 October 2026). The effective retention is the plan's maximum (`retention_months`, none on the free and self-hosted plans) or the administrators' shorter choice of 24, 12, 6 or 3 months, whichever is shorter (`usage_retention` in `apps/server/aift/policies.py`). When a period applies, it is a rolling N-calendar-month window in the company's configured IANA timezone. Calculate a daily cutoff from the start of the current local day by subtracting N calendar months with end-of-month clamping, then convert to UTC; use one frozen cutoff for a cleanup job. Retain request families with dispatch time at or after the cutoff; remove an older request with all child attempts/revisions/estimates, even if one contribution crosses the cutoff. Disclose the family-based boundary rather than leaving orphan attempts. Paid/exception policies may set a different maximum; self-hosted default is indefinite until admin deletion.

Imported numeric history uses a distinct until-deletion retention class. It is not expired by the live age cutoff or by the age of its source message. Keep the original source date and the later import time separately, together with numeric measurements, coverage and the original method assessment. The extension, server, queries, exports, caches and restore rules must preserve this distinction. An age-retention marker is not an explicit history erasure instruction; ambiguous legacy markers must not be reclassified without evidence.

Explicit range/account erasure remains authoritative for imported history within the scope where it was made. Reopening a conversation must not restore records erased by a range or single-message erasure in the current scope. Range-erasure previews and confirmation disclose included undated imported records. Personal Clear removes every imported value and recorded request and starts the extension from scratch: no deletion markers or erasure key survive it, so a conversation reopened afterwards is imported and estimated again as new history.

The expiry worker runs at least daily; normal API queries exclude already-expired families even if cleanup is pending, and report the effective coverage start. Expiry removes observations, versions, estimates, affected rollups, caches and server exports. Rebuild partial affected buckets and store minimal cutoff/erasure evidence. It never retains an undisclosed all-time usage total behind a retention promise. Increasing retention later cannot recreate deleted history.

Apply the live organization retention policy consistently to local live records, their pending queues and cached snapshots. Imported numeric history has separate retention until explicit deletion, including imports associated with expired live records. A live `retention_expired` acknowledgement must not erase or block that imported history. Personal-only history has no company retention policy and remains until the local user deletes it or browser storage is lost. Before upload, fetch current policy/deletion state; the server rejects expired live records with a terminal `retention_expired` acknowledgement, and the client purges the affected live data with a visible count, rather than retrying forever or rewriting occurrence time. Use monotonic recorded cutoffs and a trusted server-time anchor; a changed local clock cannot restore expired live records. When offline, use the last valid policy and report its age, never claim the device received a newer rule.

Plan changes that shorten retention require a preview of affected records and an explicit authorized acknowledgement of the effective time and irreversible deletion. An expiring override must disclose its scheduled reversion when granted, remind admins beforehand and retain that accepted schedule. Do not retroactively delete under an unpublished policy. Any still-unacknowledged material change remains pending and alerts the operator; it is not permission for silent extra retention or silent deletion. The operator must resolve the transition before its intended effective time.

Backups have a separately disclosed proposed 30-day expiry. A restore replays both deletion markers and current retention cutoffs before serving data or accepting uploads. It must not resurrect expired data, even if a backup predates expiry or a newer plan would retain data longer. Downloaded external exports and offline installations cannot be remotely guaranteed erased; show coverage and responsibilities honestly.

Connection IP addresses are not collected since 18 October 2026 (owner decision of 17 and 18 October 2026) unless an operator switches `ip_collection_enabled` on (off by default; CONTRACTS section 8); rows stored before then are not shown to anyone and are removed, with their equality tokens, by the one-off purge command, and deleting a person still deletes that person's rows. Abuse-protection rate rows keep only a keyed hash of the address with recent request times and are deleted one day after their last request. OTP challenge lifetimes, Brevo's one-month mail logs and usage retention remain separate controls. Login-security metadata is not AI adoption data and requires its own minimal documented retention; do not reuse unlimited proxy logs as an IP archive.

## 8. Roles and platform operator

Organization roles are exactly `user` and `admin`. All active admins have the same organization permissions and may promote/demote existing verified active users. Use expected membership version, idempotency key, transaction/row locks and atomic last-active-admin protection, including concurrent demotion, deletion and suspension. Role changes are audited and invalidate privileged access promptly. A user cannot grant themselves a role by changing a URL, client state or API field. Follow the full [role contract](BRAND-ROLES-AND-DESIGN-HANDOFF.md).

The operator surface is a separate application/origin with isolated host-only sessions and explicit operator grants bootstrapped from deployment-controlled configuration. Proposed authentication uses a separate purpose-bound email OTP flow for allowlisted operator emails, never automatic promotion from an organization session. This does not introduce a third organization role. Production operators must explicitly accept this mailbox-compromise risk or choose a separately reviewed stronger operator policy; do not impose that choice on organization users.

Operator abilities: view organization/plan/provisioning health, suspend or restore hosted service with audit, configure plan versions, assign plans and grant/revoke free exceptions. Do not expose employee prompts (none exist), decryption keys or raw employee usage/IP by default. Support access to tenant-sensitive records needs a separately authorized, audited scope; being the host does not justify a hidden impersonation endpoint. UI screens O01-O06 map to these functions, not employee extension features.

## 9. Service records and authorization invariants

Required persisted groups, additional to observation/estimate tables in Contracts:

- Registration drafts, expiring domain claims and resumable provisioning jobs.
- Organizations with deployment mode, a server-generated internal key, public origin (the hosted address or the self-host origin), work domain, status, policies and approved domain claims.
- Tenant-scoped users, encrypted verified email identities, memberships with exactly two roles, membership version/status and consent/disclosure receipts.
- Purpose-bound OTP challenges, minimal delivery attempts, web sessions, first-admin bootstrap transactions, installation connections/enrollment eras, per-installation credentials/reconnect proofs and deletion-receipt capabilities.
- Versioned plan definitions, organization entitlements, operator exceptions, operator grants/sessions and audit history.

Use composite tenant/user foreign keys throughout. At the hosted address the request's own credential (Bearer token, web session, refresh token, connection ID, email-code challenge or deletion-receipt credential) determines tenant context; a self-hosted server uses its validated host, and credentials must agree with it. Never trust a submitted company ID, arbitrary `Host`/forwarded-host value or permissive sibling-origin CORS. Keep trusted ingress host/proxy configuration explicit. Self-host mode rejects unconfigured tenants. Background jobs, exports, caches and lookup keys carry tenant scope, not just HTTP handlers.

Exactly one OTP redemption creates a web session. Do not add a second `/admin/session` redemption of the same consumed code. Exactly one installation exchange creates a device. Idempotent retries retrieve the same committed result with the same authenticated proof; they do not bypass expiry/revocation or create a new identity.

## 12. Authentication and hosting payload contract

P0 generates strict TypeScript/Python DTOs from these fields plus the endpoint table in Contracts. Reject extra properties, use bounded strings and enums, and never echo submitted email/code/proof in errors. Proposed structural defaults: UUID identifiers, 200-character company/contact names, 254-character work email, 2-character country code, validated DNS-name/HTTPS-origin types, opaque cryptographic proofs and monotonically increasing integer entity versions. These bounds are product input validation, not proof of legal identity.

| Request | Required fields and result contract |
| --- | --- |
| Registration | `company_name`, `website`, `country`, `work_domain`, `admin_email`, `registrant_name`, `registrant_role`, `terms_version`, `disclosure_version`, `authority_acknowledged`, `idempotency_key` (no address field since 13 October 2026); returns `registration_id`, `state`, `expires_at`, safe validation errors and next verification step. Hosted verification signs the administrator in at the registration origin and returns `/admin`; self-hosted verification returns the bootstrap destination |
| OTP request/resend | `purpose` (`registration`, `login`, `action_reauth`; separate operator endpoints use `operator_login`), `email`, `dispatch_id`, and `registration_id` for registration; email is accepted only at initial request and must match the stored registering recipient for registration; returns opaque `challenge_id`, delivery state, expiry and retry time, never role/account/organization existence. Resend also accepts an extension `connect` challenge |
| Connection code request | `email`, `dispatch_id` at `POST /v1/connections/otp/request`; purpose `connect`. Organization selected by email domain at the hosted origin or by host when self-hosted; free-mail domain `work_email_required` at once. Returns the same challenge result as OTP request |
| OTP verify | `challenge_id`, `code`, `verification_id`; tenant/recipient/purpose come from stored challenge, not mutable body fields. Returns an administrator web session with destination `/admin` (anyone else `admin_required`, no session), verified registration continuation, or narrowly scoped recent-action authorization according to purpose. Atomic replay handling never reuses a consumed OTP to mint another principal. |
| Connection creation | `verifier_challenge`, `challenge_method` fixed to `S256`, `browser_family`, `protocol_version`, `operation_id`, `challenge_id`, `code`; optional resume pair is `resume_device_id` plus `installation_reconnect_secret`, accepted only together.
